# Writing +page.md content: markdown gotchas, house rules, page markup

Moved from CLAUDE.md on 2026.10.20 without rewriting. Words like "above" and "below" may now point to another file in `docs/engineering/` or `.claude/rules/`; the index at the end of CLAUDE.md lists them all.

## Architecture (continued)


**External links open in a new tab, `nofollow`, automatically, everywhere.** `src/lib/theme/markdown/external-links.ts` wires a `rehype-external-links` plugin into the rehype pipeline above: any link in `+page.md` content (citations, prose links, image-links) pointing at a different hostname than `SITE_URL` gets `target="_blank" rel="nofollow noopener noreferrer"` plus an appended icon and `.cw-sr-only` "(opens in new tab)" text, no per-link markdown authoring needed. The same `isExternalHref`/`externalLinkAttrs` helpers (`src/lib/site.ts`) are applied by hand in the few places the theme renders a hardcoded link from data rather than markdown (`Navbar.svelte`'s nav links and GitHub icon link, `PageLayout.svelte`'s edit link, `SidebarGroup.svelte`). **One real gap, confirmed by reading SveltePress's own bundled source:** a raw inline `<a href="...">` HTML tag typed directly into a `.md` file's body bypasses the rehype pipeline entirely and never gets auto-patched (SveltePress runs `remark-rehype` with `allowDangerousHtml: true` but no `rehype-raw`, so raw HTML stays an opaque string node no rehype plugin can see). Adding `rehype-raw` to close this was deliberately **not** done: it would also reparse every existing `<PatternCard>`/`<DensityChip>`/`<Citation>` component tag through an HTML5 parser that lowercases unrecognized tag names, breaking `<PatternCard>` into `<patterncard>` across every pattern page. **Always write links in `.md` content as `[text](url)`, never as a raw `<a>` tag.**

**Standard markdown images are the exact opposite case: write them as a raw `<img>` tag, never as `![alt](url)`.** SveltePress's own markdown pipeline converts every `![]()` into an `<enhanced:img>` custom element, meant to be compiled into a real `<img>`/`<picture>` at build time by `@sveltejs/enhanced-img`'s Vite plugin (`enhancedImages()`) — but that plugin isn't registered in `vite.config.ts`, so the tag passes straight through to the browser as an inert, unrecognized element: no image, no error, no console warning, nothing in Network either (confirmed live on `guide/scale-hierarchy/+page.md`, the first page on the publication to actually embed a content image). Registering `enhancedImages()` was considered and rejected: the package is explicitly experimental (pre-1.0), and its own resolver can't `import` a file that lives in `static/` (SvelteKit's public dir isn't part of Vite's module graph) without a special `/static/`-prefixed path convention its own error message documents — real, but untested, complexity to take on for a handful of images across the publication. A raw `<img src="/path/to/file.png" alt="...">` tag sidesteps all of it: same "content the auto-pipeline doesn't handle, write real HTML instead" convention already used for `[Citation.svelte](src/lib/theme/components/Citation.svelte)`'s `<span id="ref-N">` anchors, and it survives `allowDangerousHtml`'s opaque-string passthrough unmangled since `img` is a real HTML5 tag name (same reasoning as `<span>`, see the raw-HTML note above). If a future need for real build-time image optimization (responsive `srcset`, avif/webp) comes up across many images rather than one, revisit wiring in `enhancedImages()` properly then, including the `/static/`-prefix path handling — not before. **Four Foundations pages now carry one such illustration each** (added 2026.09.14, hand-placed by Kevin directly rather than through a session): Scale Hierarchy, Density Tiers, Street Types & Classifications, and Design Speed & Speed Limits, each a single PNG under `static/diagrams/` (`{page-slug}-diagram.png`) placed as the first element right after the page's `<script>` block (before `<RelatedMedia>` on the two pages that also carry one — the illustration leads, Related Media follows). `base.css` gives every standalone raw `<img>` in page prose a themed rounded-corner/hairline-border/shadow treatment automatically (`.cw-content > img` for an img that's its own top-level block, `.cw-content p > img:only-child` for one CommonMark wraps in a paragraph) — no per-image class needed, this applies to any future illustration added the same way.

## Architecture (continued)


**Content pages** live in `src/routes/`, one folder per URL segment, each with a `+page.md` (YAML frontmatter + GitHub-flavored markdown). SveltePress lets Svelte run inside markdown, so pages can `<script>` import theme components directly. Admonition blocks (`:::note`, `:::tip`, `:::warning`, `:::danger`, `:::unsourced`) are implemented in `src/lib/theme/markdown/admonitions.ts` via `remark-directive`; `:::unsourced` always renders in the reserved amber regardless of surrounding content, by design, so unsourced claims stay easy to spot before publication.

## Architecture (continued)


**Real gotcha hit building `IllustrationInsteadSee`:** markdown link syntax (`[text](url)`) does not resolve when it sits inside a component that is itself nested inside another component's children — confirmed live, it rendered as literal bracket text (`[Boulevard](/patterns/...)`) instead of a link, even after ruling out indentation/code-block misinterpretation as the cause. No page anywhere on this site nests a markdown link inside a component slot (every existing markdown link sits in top-level page prose); `IllustrationInsteadSee` now takes a structured `links` prop (`{ label, href, id, joiner? }[]`) and renders real `<a>` tags itself instead, the same "hand-render an internal link from the component" pattern already used by `PageLayout`'s edit link and `Navbar`'s nav links. If a future component needs to show a link inside a doubly-nested slot, use this same structured-prop pattern rather than markdown link syntax.

**Two more precise root causes found for this same general class of bug, while building the Speed & Modal Hierarchy card (2026.09.02) — both now-understood special cases of "content inside a nested component slot isn't parsed as markdown the normal way," not two separate bugs:** (1) Indenting a markdown-embedded Svelte component's content by 4+ spaces for source readability, when that content starts right after a blank line, gets parsed as a CommonMark indented code block, silently breaking any markdown inside it (an ordered list rendered as literal `1. Pedestrian` text, and swallowed a same-line raw `<a>` tag into the code block where it rendered as escaped text instead of a link). Fix: never indent multi-line component content, even though every sibling tag around it is indented — write it flush left. (2) A markdown-embedded component tag carrying a complex prop value (an object or array literal, e.g. `rows={[{ tiers: [...] }]}`) fails CommonMark's own HTML-block-recognition regex and gets treated as plain paragraph text instead of a component, **specifically when a blank line immediately precedes it** — confirmed by the exact same tag succeeding once the blank line above it was removed (making it a continuation of the prior tag's line instead of a fresh block) and failing again when the blank line was restored. A tag with only simple string/number attributes doesn't hit this. Fix: never put a blank line directly before a component tag that has an object/array-literal prop; self-closing vs. open+close tag form didn't matter once this was fixed. Both fixes are now baked into every page using `SpeedModalHierarchyCard`/`SpeedLimitSection`/`ModalHierarchySection` — copy their markdown structure (flush-left, no blank line before a complex-prop tag) rather than the more readable indented style used elsewhere on the site, if adding a similarly nested component in the future.

## Self-reference terminology audit and corrections, Item 11 (2026.09.10)

**Locked house rule, applies to every `+page.md` and `README.md` going forward:** self-reference to this project's own format/medium (calling the publication a "website," "site," or "book") corrects to **"the publication."** Self-reference to the guidebook's content as a whole using generic "guide" corrects to **"the guidebook."** "The system" is already correct for the framework itself and needed no changes. `CLAUDE.md` itself is explicitly exempt from this rule (internal dev doc, not reader-facing) — don't apply it here if editing this file.

**The load-bearing exemption, easy to get backwards:** "the Guide" (capitalized or not) referring to _this site's own `/guide/` section specifically_ — as opposed to the whole publication — is a legitimate proper-noun section name, the same status as "Patterns" or "Retrofit Strategies," and stays exactly as written. Test before touching any "guide" instance: **does the claim hold true across Patterns and Retrofit Strategies too, not just the Guide section?** If yes, it's whole-publication self-reference and needs correcting to "guidebook." If no (it's really about that one section, or names it by contrast with Patterns/Retrofit Strategies), leave it alone. Concretely: "Every pattern in this guide..." fails the test (patterns live under `/patterns/`) and becomes "guidebook"; "The Guide is where you start" or "published under Guide → Make It Happen" passes and stays "Guide."

**Other real exemptions found doing this audit, worth knowing before touching this class of word again:**

- Real citation/external-document titles in body prose, not just inside a `## References` list — "AASHTO's Green Book," "NACTO's Urban Street Design Guide," "Guide Sign" (a real MUTCD sign-category Element pattern, `ELM-GDS-13`, nothing to do with this site's Guide section) — never touch these regardless of where they sit on the page.
- `/about/brand-guide/` is a special case: the whole page transcribes an external "working brand reference" document (the companion `commonway-brand-guide.html`, see Content model notes below), so every lowercase "the guide" on that specific page ("the guide doesn't define...", "the guide's own four ramps", "per the guide") refers to _that external source_, not to this site's own guidebook — left unchanged throughout, a page-specific pattern that doesn't generalize elsewhere.
- "Site" has a real, unrelated physical-construction-site meaning that surfaces specifically on Facilities/Elements pattern pages (siting a bike-share station, a transit shelter, an RSA field review) — a genuine false-positive category, not self-reference at all.
- Technical/developer-facing descriptions of the underlying stack or hosting stay as written when the description is the predicate, not the self-referential subject: "a SveltePress site," "a static site" stay; but "**This** site is hosted as a static site" still gets its subject corrected to "**This** publication is hosted..." — the site/publication swap always applies to the sentence's own self-referential subject, regardless of what technical predicate follows it.
- Two one-off generic analogies stay as written: `about/contributing/+page.md` and `README.md` both use "...the same way a publisher retains rights to a book that many people contributed research to" (a generic publishing analogy, not about this publication specifically); `patterns/freeways/default/+page.md` uses "a detailed design guide" as a generic industry-category term.

**Left flagged, not corrected, still open:** `guide/design-speed/+page.md` has three instances of generic "a pattern book"/"a pattern-book user" framing (as opposed to the same page's clearly self-referential "in this book," which was corrected) — genuinely ambiguous whether that's self-reference in generic clothing or a true generic statement; and the 2026.08.28 changelog entry's "Guide structure established..." wording, left alone under the existing "historical changelog entries stay as written" convention (see the Parkway ID renumbering note below) even though it predates the Guide/Patterns split and might originally have meant the whole publication.

## Content model notes

- **`PageLayout.svelte` renders an `<h1>` from the page's frontmatter `title` automatically** (see `{#if fm.title}<h1>{fm.title}</h1>{/if}` in `PageLayout.svelte`). Do not start a `+page.md` body with a `# Heading` that repeats the title, it duplicates the h1. Existing pages (`guide/` bare root, `guide/how-to-read-a-pattern`, etc.) go straight from frontmatter into body text or an `##` subheading; follow that pattern for new pages.
- A companion brand guide (`../commonway-brand-guide.html`, outside this repo) defines the real, locked CS visual system: base colors (ink `#141414`, paper `#FDFAF3`, teal `#00A896`, indigo `#3D3AAB`, reserved amber `#FF9F1C`), a colorblind-checked 6-step Functional Classification × density ramp, and the Fraunces/Inter type scale. `tokens.css` is synced to it (see above); the guide itself doesn't cover dark mode, so every dark-mode value in `tokens.css` is a site-only extension, reasoned out and documented inline rather than specified by the guide.
- CS editorial rules that apply to any `+page.md` content written in this repo: no em-dashes anywhere, plain-language term introduced before its formal/technical name, citations follow a specific numbered/dated agency-reference format (see the brand guide for the full citation and evidence-tier system referenced by `Citation.svelte` and the admonition tiers), and self-reference to this project's own format ("website"/"site"/"book") corrects to "the publication," self-reference to the guidebook's content as a whole corrects to "the guidebook" — see the Self-reference terminology audit note below for the full rule and its exemptions (most importantly: "the Guide" naming this site's own `/guide/` section is not self-reference and stays as written).

- The mobile hamburger drawer (`Sidebar.svelte`, `<940px`) shows the navbar's own primary links (Home/Guide/Patterns/Reference/Blog/About) above the current page's sidebar tree, not just the tree. Both live in one `<aside>` now; the primary-nav block is CSS-hidden `≥940px` since the navbar shows those links directly there. Before this fix the drawer only rendered when the current route had a page-specific sidebar, so the navbar's own links were completely unreachable on any narrow viewport, including the homepage.

## Page polish, passes 1 and 2 (2026.10.18)

Light visual structure for content pages, approved from `mockups/page-polish-v1.html` (untracked). Kevin chose **no new build step**: pass 1 is CSS on existing markup; pass 2 was a one-time scripted edit of the page sources, not a rehype plugin.
- **Accent:** `PageLayout` sets `data-accent` on `<main>` from `pageAccent()` (`src/lib/theme/page-header.ts`): the Pattern ID's classification, a Retrofit's scale peer (RFT-CDR corridor, RFT-INT intersections, RFT-NET network), `about` for `/about/`, else `primary` (teal). Tokens `--cw-accent-soft` (tint), `--cw-accent-bar` (decoration only, never text), `--cw-accent-ink` (text on the tint, computed 6:1+ in both themes) are at the end of `tokens.css`, with dark and high-contrast values. A new Scale prefix needs a line in `PREFIX_ACCENTS` and a token block.
- **Header** (`PageHeader.svelte`, rendered by `PageLayout` for every page with a title): tinted band, `.page-head__eyebrow` label from `pageEyebrow()` (navbar section plus the sidebar group with no `to` that holds the page; `data-pagefind-ignore`, dropped from text-only/markdown copies via `DROP_SELECTORS`), and the h1. **On Pattern and Retrofit pages it is the ID card:** `fm.patternId` and `fm.status` (frontmatter, moved out of the old card tag) sit in the row, and the page body's **first paragraph is the summary**, joined to the band by CSS (`.page-head.page-head--id + p`). So a new pattern or Retrofit page has no `PatternCard`/`RetrofitCard` tag: frontmatter `status:` (patterns only), then the one-sentence summary as the first paragraph after `<script>`, then `<PatternViewer ... />`. `PatternCard`/`RetrofitCard` were removed on 2026.10.20; documentation samples use `<PageHeader demo accent="..." summary="..." ... />` (title drawn as a `p`, no second h1). With Color symbols on, `.page-head__sym` shows the tab beside the ID.
- **Pass 1 CSS hooks (base.css "Page polish"):** a paragraph right after the header whose only element is one `<em>` is the subtitle (7 pages); the next paragraph (or the first, without one) is `--cw-text-lg`. Heading bars only on `.cw-content > h2` (direct children, never component headings). Tables: only markdown tables, marked `cw-table-wrap--md` by `table-scroll.ts`. Callout icons are Lucide CSS masks (`data:` images are allowed by the CSP). References panel: `.cw-content > h2#references` plus the `ol` right after it.
- **Pass 2 markup (one-time scripted edit, committed in the pages; no build step does it). Write new content the same way:**
  - IDs in prose: `<IdPill id="LOC-DEF-01" />` instead of `(LOC-DEF-01)` (renders the parentheses visually hidden; import `IdPill`). Not inside link text, tables or headings.
  - Related patterns / Target patterns / Related retrofit strategies / Retrofit path options: `<div class="cw-links">` + blank line + a markdown list, one `- [Name](/url/) <IdPill id="..." /> (note)` per entry, + blank line + `</div>`. One card per pattern or strategy: never put two links in one entry, except an "X with Y" Target pattern that is a single destination. A note shared by a group ("A, B, C (contrasting topologies)") goes on the last entry only (Kevin's call, 2026.10.18). An entry must start with its link (the card styles the first link as the title); an entry with no link gets a dashed card. Sections written as sentences stay as prose.
  - Retrofit pages: `<div class="cw-facts">` around four `<div class="cw-fact">` blocks, one per section (Applicability and thresholds, Evidence and effectiveness, Getting it built, Who can move this); icons are keyed to those heading ids.
  - `<div class="cw-context">` around the "Typical at" paragraph (label wrapped in `<span class="cw-context__label">`) and its note paragraph.
  - `<div class="cw-tiles">` around a short list (6 items or fewer) whose items all start in bold; `<div class="cw-fields">` around catalog-field runs ("**What it is.**"); `<div class="cw-options">` around other runs of bold-led paragraphs, `cw-options cw-options--pair` for exactly two; `<div class="cw-ranked">` around step or ranking ordered lists (not References).
  - Numbered headings/table cells: `<span class="cw-num">1<span class="cw-num__dot">.</span></span>` (heading ids and On this page text are unchanged).
  - Every wrapper needs a blank line after the opening tag and before the closing tag, or the markdown inside isn't parsed. Tested: headings inside a wrapper keep their ids and appear in On this page. Wrappers go only at the top level of the page, never inside a component's slot.
- The script (`polish.py`, scratchpad, not kept) skipped the Brand Guide and the two How to Read pages (edited by hand) and the privacy policy's bold-led paragraphs; `accessibility-policy` keeps its long bold-led lists as plain lists (tiles only for short items).

## Website Specification audit, `/about/website-audit/` (2026.10.14) (continued)

**Real bug found and fixed along the way: a component tag split across several lines in a `+page.md` gets wrapped in `<p>` by the markdown parser** (CommonMark only starts an HTML block for a complete one-line opening tag), and browsers auto-close that `<p>` around block content, so hydration fails and Svelte re-renders the page from scratch (console: `Failed to hydrate: HierarchyRequestError`). This was live on the homepage (`<Hero` and `<EvidenceStrip` were multi-line). **Keep every component tag's opening tag on one line** in markdown. Check: `find src/routes -name '+page.md' -print0 | xargs -0 grep -nE "^\s*<[A-Z][A-Za-z]+(\s[^>]*)?$"` (the one remaining hit, inside Stroad's `<Illustration>`, is nested content and hydrates fine).
