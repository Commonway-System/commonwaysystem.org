### Commands (continued)


**Package manager is pnpm, not npm**, despite what `README.md` says: `pnpm-lock.yaml` and `pnpm-workspace.yaml` exist, there's no `package-lock.json`. The `npm run <script>` commands above are fine, they just invoke `package.json` scripts against the existing `node_modules`. But running plain `npm install` to add or update a dependency tries to re-resolve the entire tree with npm's own resolver against a pnpm lockfile, which is both wrong and extremely slow (minutes, not seconds, in testing). Use `pnpm install` for any dependency change.

There is no test suite and no lint script configured. `pnpm run check` (svelte-check) is the only automated verification step; run it after any change to `.svelte` files or theme TypeScript. It does not catch visual regressions, always check UI changes in an actual browser (see "Working conventions" below). It also does not catch a broken internal link, since that's a prerender-time check: `pnpm run build` fails outright on any same-page `#id` link or route with no matching target, thanks to `adapter-static`'s `strict: true` (see Citation.svelte's note below) — run a real build, not just `check`, after adding pages with a lot of cross-links (a pattern index, a typology-index page, etc.).

**`pnpm add`/`pnpm install` can fail with `ERR_PNPM_IGNORED_BUILDS`** if any dependency (including a transitive one, e.g. `sharp` pulled in by SveltePress's image plugin) has a native build script pnpm's default policy won't run without approval. `pnpm approve-builds` is the normal fix but needs a TTY, unavailable in a non-interactive session; the actual fix is `pnpm-workspace.yaml`'s `allowBuilds:` map (`allowBuilds: { sharp: true }`, one entry per package name) — the non-interactive equivalent, and what's committed here. If this error resurfaces for a new dependency, add its name there rather than fighting the interactive prompt.

### Architecture

This is a [SveltePress](https://sveltepress.site/) site (SvelteKit + a SveltePress theme plugin) with a **fully custom theme** — not the SveltePress default theme reskinned, but built from scratch to keep only its layout shell (sticky navbar, collapsible sidebar, on-this-page rail, prev/next footer) and replace all branding, components, and styles with Commonway System (CS) ones.

**Theme registration flow:** `vite.config.ts` calls `commonwayTheme({...})` (defined in [src/lib/theme/index.ts](src/lib/theme/index.ts)) and passes the result into the `sveltepress()` Vite plugin. `commonwayTheme` is the SveltePress theme contract: it points to `GlobalLayout.svelte` / `PageLayout.svelte` as the layout components, registers the Shiki highlighter, and wires remark/rehype plugins (`remark-gfm`, `remark-directive` for admonitions, `rehype-slug` + a custom heading-anchor plugin, `externalLinks` for automatic external-link handling, `tableScroll` for the scrollable-table wrapper, see below). Theme options (site title, nav, sidebar, GitHub link, edit-link template, footer note, Google Analytics ID) are passed through a virtual Vite module (`virtual:commonway/options`, see `optionsPlugin` in `index.ts`) so theme components can import them without prop-drilling.

**Wide tables scroll horizontally in their own box instead of overflowing the page.** `src/lib/theme/markdown/table-scroll.ts` (a rehype plugin) wraps every markdown `<table>` in `.cw-table-wrap > .cw-table-scroll > table` plus a small hidden-by-default "scroll for more" hint, at build time — no per-table authoring needed, this applies to every table on every page automatically. `base.css`'s `.cw-table-*` rules add a CSS-only scroll-shadow (the Lea Verou two-gradient trick, no JS) and a themed thin scrollbar to `.cw-table-scroll`; `src/lib/theme/layout.ts`'s `initTableScrollHints()` (called from `GlobalLayout.svelte` on mount and after navigation) measures each table and only shows the hint text when a table actually overflows. Deliberately a wrapper div, not CSS `display: block`/`overflow-x` on the `<table>` element itself (an earlier version of this fix): forcing a table's own computed `display` off `table` strips its implicit ARIA table/row/cell roles in some browsers, breaking screen-reader table semantics — the wrapper keeps the table's native display untouched. A simple 2-column table still renders at full width with no scrollbar; only a table wide enough to need it (many columns, or long unbreakable content) triggers the scroll box.

**`vite.config.ts` is the single source of truth for site content structure** — navbar links, the manual sidebar tree (keyed by route prefix, e.g. everything under `/guide/` uses the `sidebar['/guide/']` entry), GitHub link, edit-link template, site title/description. This is the file to edit for day-to-day content/nav work; `src/lib/theme/` should rarely need touching once the visual direction is set. The sidebar shown for any page is whichever key in `sidebar` the current URL starts with (same model as SveltePress's own default theme). There is no auto-generated sidebar from the routes folder — it's manual by design, since it needs to map onto the Functional Classification / density-tier hierarchy rather than a generic path tree.

**"Last updated" date** (`PageLayout.svelte`'s footer, next to "Suggest changes to this page"): sourced from `src/routes/+layout.server.ts`, which runs `git log -1 --format=%cI -- <that route's +page.md>` once per route at build time and formats the result, `null` (no line rendered) if the file has no commit yet or git isn't available. **Navbar CalVer version (fixed 2026.09.01):** `Navbar.svelte` no longer computes its own version — it reads `page.data.siteVersion`, set by `siteVersion()` in the same root `src/routes/+layout.server.ts` described above (`src/lib/site.ts`'s `calVerToday()` is gone; `formatCalVer(year, month, day)` is its pure-formatting replacement, called from both branches below). The original design (a plain `new Date()` read wherever `calVerToday()` was called) worked in `pnpm run dev` but was wrong in production: a prerendered build's wall clock reflects whenever Netlify happened to actually run that build, not the date of the commit being built, and those two dates silently diverge any time Netlify rebuilds the same commit later without a fresh push (a manual "Trigger deploy" / "Clear cache and deploy site" click, or an automatic retry) — confirmed live on 2026.09.01, when the navbar showed a date one day ahead of every page's own git-derived "Last updated" text after exactly that kind of same-day rebuild. `siteVersion()` fixes this by keying the version to the actual last commit's date (`git log -1 --format=%cI`, no path filter, i.e. `HEAD`) instead of the wall clock, gated on SvelteKit's `dev` flag from `$app/environment`: `pnpm run dev` still shows a live current-date read (there's no meaningful "last commit" to key off mid-edit), but `pnpm run build`/`pnpm run preview`/the real Netlify build all show the last commit's own date, which only changes when new content is actually pushed, and stays identical no matter how many times that same commit gets rebuilt. If this ever needs re-diagnosing: compare the navbar version against any page's own "Last updated" text — they're computed by the same `git log` mechanism now and should never disagree the way they did before this fix.

### GuideDiagram, the img/height:auto bug, and AuthorPhoto (2026.09.22)

**`src/lib/theme/components/GuideDiagram.svelte`** replaces the raw `<img>` tag on the four Foundations pages that embed a full-width topic diagram (Density Tiers, Design Speed & Speed Limits, Scale Hierarchy, Street Types & Classifications). `src`/`alt` are required, matching the raw tag's own required attributes; four more props are optional and independent of each other: `width`/`height` (real pixel dimensions as actual HTML attributes, not CSS — lets the browser reserve the image's layout space from its own attribute-derived aspect ratio before a lazy-loaded image finishes downloading), `aspectRatio` (a CSS `aspect-ratio` string, for when the ratio is known but not the exact pixel size — ignored if `width`/`height` are both given), and `caption` (wraps the image in a real `<figure>`/`<figcaption>` instead of a bare `<img>`, no extra ARIA needed for that semantics). ### Working conventions on this repo

- **Accessibility check on every change** (axe + a whole-page accessibility review, however small the edit) is a standing rule, described in full in its own section near the top of this file. Treat it as part of "done" for any page, component, or style change.
- **Visually verify UI changes in the browser before calling them done**, not just `npm run check` (which won't catch a badge rendering illegibly small, a color barely visible in dark mode, or a hidden character leaking into visible text, all real issues found this way in past sessions). Check both light and dark mode, and at least one narrow viewport width, since this theme has real behavior differences at 940px and 560/480px breakpoints.
- **After drafting page content from a written ticket/instruction file, re-read the rendered section specifically for sentences addressed to Claude rather than to a reader** (a real, confirmed failure mode, not hypothetical — see the Bicycle Boulevard leaked-note bug in the Ticket G-J note above). A ticket file mixes real page content with meta-commentary about that content ("this citation also appears in callout 3 above," "add this verbatim," section-placement notes); it's easy for a sentence explaining _where else_ something appears to get pulled in as if it were prose for the page. A plain read-through of the finished section, asking "would a reader be confused by this sentence," catches it; `pnpm run check`/`pnpm run build` won't, since it's valid markdown that renders and links fine.
- **Compute contrast ratios rather than eyeballing color choices.** A short Python snippet (WCAG relative luminance formula) is fast and has repeatedly caught real problems eyeballing missed, e.g. the real Brand Guide amber turning out to be only 1.97:1 as a focus ring against light paper.
- When a fix surfaces an adjacent problem (a token value fix revealing a component that also needs to change, for instance), **fix genuine bugs and contrast failures directly**, but **flag pure design/content-semantics judgment calls** rather than deciding them, see "Known gaps" above for the current list of flagged-not-fixed items.
- This is a static site (`adapter-static`, deploying to Netlify). Anything touching routing, build output, or server-side code should be checked against that constraint, e.g. a new `+server.ts` endpoint needs `export const prerender = true` and, if nothing links to it, an explicit entry in `svelte.config.js`'s `kit.prerender.entries`, or it silently won't exist in the deployed build.
- **Before pushing to `main` (a push is a publish, see Deployment above), follow the publishing checklist described on `/about/release-history/`:** draft a short build note covering what content changed, what structural/site changes shipped, and anything left in a known-incomplete state, then use that note as both the commit message and a new entry in `src/lib/data/releases.ts` (newest first; one `changes` item per change, see "Changelog format" below). The site's CalVer version (shown in the navbar) is computed from the last commit's own date via `siteVersion()` in `src/routes/+layout.server.ts` (see that file's note above), so it tracks the push date rather than whenever Netlify happens to run a build; the changelog's own `releases[0]` should match what actually shipped that day, not be left stale.
- **`vite.config.ts`'s sidebar is a manual tree, `git status`/`git add` don't know about it**: adding a new page also means adding it to the relevant `sidebar['/...']` entry and, if it should show up in the Pattern Index, to `src/routes/patterns/+page.md`'s list too, or it exists but is unreachable via navigation.
- **On visual/landing-style work (the homepage build, its later redesign pass), the user wants real editorial polish, not a plain content-column render**, and will say so plainly if a first pass reads as flat or dated ("looks like an old-school 2000s site"). Concretely, this has meant: full-bleed sections that break out of the sidebar/toc grid and the 46rem prose column (see the `isHome` full-bleed pattern and the `wide` frontmatter flag, both in the Hero/EvidenceStrip/FeatureGrid note above), deliberate background contrast between sections rather than one flat page color, subtle motion (gated behind `prefers-reduced-motion`, never the only way to convey something), and named color/background treatments matching what a UI element is actually _for_ (the differentiator strip's amber-to-teal swap: amber read as a warning, not a feature highlight) over "was it the closest existing token." - **Pushing to GitHub needs `GITHUB_TOKEN` from `.env`** (gitignored, never commit it): the `origin` remote is HTTPS (`https://github.com/Commonway-System/commonwaysystem.org.git`), not SSH, so a plain `git push` has no credential source of its own in a fresh environment. Use the token for that one push rather than assuming an SSH key or a cached credential helper is present. **Push procedure used 2026.09.26 (worked):** commit with the changelog build note as the message (end it with the attribution line the session's system reminder specifies), then push without writing the token into git config or the remote URL: `TOKEN=$(grep '^GITHUB_TOKEN=' .env | cut -d= -f2-); git -c http.extraheader="Authorization: Basic $(printf 'x-access-token:%s' "$TOKEN" | base64)" push origin main`. - **When a new content catalog needs its own index-card and detail-card components (Retrofit Strategies mirroring Patterns is the precedent so far), mirror the sibling component's mechanics exactly (image treatment, number-badge mechanism, hover states, shared layout utility class) rather than inventing new ones, and derive the new component's coloring from whichever existing classification is its closest functional/semantic peer instead of a separate palette.** Concretely: `RetrofitIndexCard`/`RetrofitCard` reuse `PatternIndexCard`/`PatternCard`'s exact shell and the `.pattern-index-grid` layout class, and Retrofit Strategies borrow Pattern classification colors (Intersection-scale strategies get the real Intersections & Crossings ramp, since Intersection patterns already have one; Corridor/Network strategies share Patterns' own still-placeholder Freeway-gray). Silently translate pure authoring-syntax mismatches to the site's real conventions; verify-then-fix (not just flag) a literal value that turns out to fail contrast or another concrete correctness check; still flag actual content/design judgment calls (a ticket reversing a documented convention, like Ticket B's intersection status badges, was confirmed with the user before proceeding, not decided unilaterally either way).
