## Commands

```sh
pnpm install       # NOT npm install, see below
pnpm run dev        # dev server, usually http://localhost:5173
pnpm run build      # static build to build/ (HTML/CSS/JS, no server needed at runtime), then in order: scripts/generate-text-pages.mjs (text-only pages in build/text/, a markdown version of every page at build/<route>.md, build/llms-full.txt), scripts/generate-agent-files.mjs (build/<route>.jsonld + schemamap.xml, the OKF bundle in build/okf/ + okf.tar.gz), scripts/build-search-index.mjs (Pagefind index in build/pagefind/), scripts/make-thumbs.mjs --check (warns about missing image thumbnails)
pnpm run preview    # serve build/ locally to sanity-check the static output
pnpm run check      # svelte-kit sync && svelte-check --tsconfig ./tsconfig.json
pnpm run thumbs     # make the small copies (160px and 480px WebP) of any new or changed content image, then COMMIT them
node scripts/qa/netlify-like.mjs build 5180          # serve the BUILT site like Netlify (applies static/_headers incl. CSP, gzip, 404.html); also preview_start "commonway-build"
node scripts/qa/qa.mjs http://localhost:5180 / /about/   # axe + console warnings (CSP, hydration) in light/dark at 1280 and 375; see the file header for --modes/--storage/--setup
python3 scripts/qa/check-headers.py                  # after a build: flags any header two _headers rules both set (Netlify merges them into invalid values)
```

The `scripts/qa/` tools are not part of the build. `qa.mjs` borrows puppeteer-core and axe-core from `/Users/kevinyoung/Documents/pro-how-com/scripts/qa/node_modules` (override with `QA_MODULES=<path to a package.json>`) and drives the installed Google Chrome, which is much faster than the in-pane iframe recipe below and runs the same tag set. Lighthouse is in the same folder: `CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" node /Users/kevinyoung/Documents/pro-how-com/scripts/qa/node_modules/lighthouse/cli/index.js <url> --only-categories=performance --output=json --output-path=out.json --chrome-flags="--headless=new"`. Compare Lighthouse only against a compressed server (netlify-like.mjs gzips), and in Puppeteer screenshots pass `captureBeyondViewport: false` or top-layer overlays (popovers, dialogs) disappear.

**Standing rule: any time an image is added or replaced for the site, run `pnpm run thumbs` and commit the new `thumbs/` files.** That means a new file in `static/patterns/`, `static/media-assets/`, `static/photos/` or `static/diagrams/` (Pattern and Retrofit illustrations, Media Gallery previews, the author photo, Foundations diagrams, which get 768/1280 px copies instead of 160/480), or a local `image:` in any page's frontmatter (a blog post's featured image, say). Search results and the Pattern, Retrofit and Media cards show those small copies, not the 1 MB originals; the script is safe to re-run (it skips thumbnails that already exist and remakes ones whose source changed) and `pnpm run build` warns `Thumbnail missing for ...` if one was forgotten (the site then falls back to the full-size image, which works but is heavy). Do this in the same session that adds the image, and mention the thumbs in the commit. Details: "Featured images and thumbnails" near the end of this file.

**Package manager is pnpm, not npm**, despite what `README.md` says: `pnpm-lock.yaml` and `pnpm-workspace.yaml` exist, there's no `package-lock.json`. The `npm run <script>` commands above are fine, they just invoke `package.json` scripts against the existing `node_modules`. But running plain `npm install` to add or update a dependency tries to re-resolve the entire tree with npm's own resolver against a pnpm lockfile, which is both wrong and extremely slow (minutes, not seconds, in testing). Use `pnpm install` for any dependency change.

There is no test suite and no lint script configured. `pnpm run check` (svelte-check) is the only automated verification step; run it after any change to `.svelte` files or theme TypeScript. It does not catch visual regressions, always check UI changes in an actual browser (see "Working conventions" below). It also does not catch a broken internal link, since that's a prerender-time check: `pnpm run build` fails outright on any same-page `#id` link or route with no matching target, thanks to `adapter-static`'s `strict: true` (see Citation.svelte's note below) — run a real build, not just `check`, after adding pages with a lot of cross-links (a pattern index, a typology-index page, etc.).

**`pnpm add`/`pnpm install` can fail with `ERR_PNPM_IGNORED_BUILDS`** if any dependency (including a transitive one, e.g. `sharp` pulled in by SveltePress's image plugin) has a native build script pnpm's default policy won't run without approval. `pnpm approve-builds` is the normal fix but needs a TTY, unavailable in a non-interactive session; the actual fix is `pnpm-workspace.yaml`'s `allowBuilds:` map (`allowBuilds: { sharp: true }`, one entry per package name) — the non-interactive equivalent, and what's committed here. If this error resurfaces for a new dependency, add its name there rather than fighting the interactive prompt.

## Accessibility standing rule: every change gets an accessibility check of the WHOLE page it touches

**This applies to every page added and every edit made from 2026.09.26 on, however small.** Fixing one illustration, one paragraph, one table cell, or one token still means checking the *entire page* (or, for a component or style change, every page type that uses it), not just the bit that changed. The site owner set this rule explicitly and it is not optional or "only for big changes." A full-site scan is **not** required per change: that is reserved for the site owner's separate Website specification audit (see the Roadmap note in the release-history section). What is required each time:

1. **Run axe on each page you touched or added**, in light AND dark mode, at desktop width AND 375px, using tags `wcag2a, wcag2aa, wcag21aa, wcag22aa, best-practice`. Recipe below. Zero violations is the bar; if one remains, fix it (or, if it is a real judgment call, flag it to the user and record it in `/about/accessibility-policy/`'s Known limitations, never silently ignore it).
2. **Do the "mindset review" that axe cannot do**, on that whole page: reading/heading order makes sense (one `h1`, no skipped levels, a card title that repeats the `h1` is not a heading); every image has meaningful `alt` or `alt=""` if purely decorative; link text makes sense out of context; color is never the only signal (a text label, icon, or pattern accompanies it); interactive things are real `<button>`/`<a>` with visible keyboard focus and a tap target of at least 24x24 CSS px; tables have real header cells; anything that moves has a pause path and respects `prefers-reduced-motion`; collapsed content (`<details>`, accordions) is checked *expanded* too; layout survives 375px width, the largest Display settings text size, high-contrast mode, and simplified view (test new components in all of them, not just a sample page); focus is not hidden behind the sticky navbar/`TocMobile` bar (`scroll-padding-top` on `html` handles this, don't reintroduce per-element `scroll-margin`).
3. **Compute contrast, don't eyeball it** (WCAG formula, see Working conventions). Text needs 4.5:1, UI components and focus indicators 3:1, in both themes and under any overlay (the pointer halo, hero art).
4. **Fix genuine failures directly; flag judgment calls.** New content pages must also be reachable by the skip link, `<main>`, and the text-only build (below) without extra work: don't bypass `PageLayout`.
5. **Keep the paper trail current:** if a fix or a new limitation changes what's true about accessibility, update `/about/accessibility-policy/` (its "Known limitations" section is the single public list; it currently says no open items from the 2026.09.26 audit remain, and lists what has NOT been tested), and mention it in that day's `/about/release-history/` entry.
6. **Say in the final report what was checked and what wasn't** (e.g. "axe clean on X in both themes at both widths; not tested with a real screen reader"). Do not claim conformance.

**axe recipe (how the 2026.09.26 audit was run; no test framework is installed).** Since 2026.10.14 the quicker route is `scripts/qa/qa.mjs` (see Commands), which drives headless Chrome directly. The in-pane recipe still works when that isn't available: the Browser pane can't run Playwright, so pages are loaded into hidden same-origin iframes of a dev-server tab and axe-core is evaluated inside each one:

```js
// in javascript_tool, on any http://localhost:5173/ page
const src = await fetch('https://cdnjs.cloudflare.com/ajax/libs/axe-core/4.10.2/axe.min.js').then(r => r.text())
const f = document.createElement('iframe')
f.style.cssText = 'position:fixed;left:0;top:0;width:1280px;height:900px;border:0;opacity:0;z-index:-1' // width 375 for the phone pass
document.body.appendChild(f)
await new Promise(r => { f.onload = r; f.src = '/patterns/collectors/default/' })
await new Promise(r => setTimeout(r, 1800))                       // let Svelte hydrate
const win = f.contentWindow, d = win.document
d.documentElement.dataset.theme = 'dark'                           // then again with 'light'
await new Promise(r => setTimeout(r, 2500))                       // theme switch animates; scanning sooner gives FALSE contrast failures
win.eval(src)
const r = await win.axe.run(d, { runOnly: { type: 'tag', values: ['wcag2a','wcag2aa','wcag21aa','wcag22aa','best-practice'] } })
r.violations.map(v => v.id + ' x' + v.nodes.length + ' ' + v.nodes[0].target.join(' '))
```

Gotchas that each cost time once: (a) a single `javascript_tool` call times out at ~45s, so start long runs as a background `async` IIFE that pushes into `window.__results` and poll with short waits; (b) the pane is usually `visibilityState: 'hidden'`, so `requestAnimationFrame`, CSS transitions and `:focus` matching don't behave (verify focus/reveal styles by forcing the state, and don't rely on rAF-driven code in tests); (c) `details` cells are collapsed until opened, and axe ignores collapsed content, so set `details.open = true` and rescan (this is how the GuidanceTable `.guidance__note` contrast failure was found); (d) axe reports "incomplete" for text over SVG shapes, tiny numeric badges, and partly-scrolled sticky panels; measure those by hand (computed colors + the contrast formula) and record the result instead of leaving them "needs review"; (e) iframes share `localStorage`, so set `commonway-display-settings` *before* loading them to test a Display settings mode, and remove it afterward; (f) a temporary helper file dropped in `static/` to load a driver script must be deleted before finishing (it would ship); (g) `pnpm run build` stops the dev server, so `preview_start` again before browser checks.

## Architecture

This is a [SveltePress](https://sveltepress.site/) site (SvelteKit + a SveltePress theme plugin) with a **fully custom theme** — not the SveltePress default theme reskinned, but built from scratch to keep only its layout shell (sticky navbar, collapsible sidebar, on-this-page rail, prev/next footer) and replace all branding, components, and styles with Commonway System (CS) ones.

**Theme registration flow:** `vite.config.ts` calls `commonwayTheme({...})` (defined in [src/lib/theme/index.ts](src/lib/theme/index.ts)) and passes the result into the `sveltepress()` Vite plugin. `commonwayTheme` is the SveltePress theme contract: it points to `GlobalLayout.svelte` / `PageLayout.svelte` as the layout components, registers the Shiki highlighter, and wires remark/rehype plugins (`remark-gfm`, `remark-directive` for admonitions, `rehype-slug` + a custom heading-anchor plugin, `externalLinks` for automatic external-link handling, `tableScroll` for the scrollable-table wrapper, see below). Theme options (site title, nav, sidebar, GitHub link, edit-link template, footer note, Google Analytics ID) are passed through a virtual Vite module (`virtual:commonway/options`, see `optionsPlugin` in `index.ts`) so theme components can import them without prop-drilling.

**External links open in a new tab, `nofollow`, automatically, everywhere.** `src/lib/theme/markdown/external-links.ts` wires a `rehype-external-links` plugin into the rehype pipeline above: any link in `+page.md` content (citations, prose links, image-links) pointing at a different hostname than `SITE_URL` gets `target="_blank" rel="nofollow noopener noreferrer"` plus an appended icon and `.cw-sr-only` "(opens in new tab)" text, no per-link markdown authoring needed. The same `isExternalHref`/`externalLinkAttrs` helpers (`src/lib/site.ts`) are applied by hand in the few places the theme renders a hardcoded link from data rather than markdown (`Navbar.svelte`'s nav links and GitHub icon link, `PageLayout.svelte`'s edit link, `SidebarGroup.svelte`). **One real gap, confirmed by reading SveltePress's own bundled source:** a raw inline `<a href="...">` HTML tag typed directly into a `.md` file's body bypasses the rehype pipeline entirely and never gets auto-patched (SveltePress runs `remark-rehype` with `allowDangerousHtml: true` but no `rehype-raw`, so raw HTML stays an opaque string node no rehype plugin can see). Adding `rehype-raw` to close this was deliberately **not** done: it would also reparse every existing `<PatternCard>`/`<DensityChip>`/`<Citation>` component tag through an HTML5 parser that lowercases unrecognized tag names, breaking `<PatternCard>` into `<patterncard>` across every pattern page. **Always write links in `.md` content as `[text](url)`, never as a raw `<a>` tag.**

**Standard markdown images are the exact opposite case: write them as a raw `<img>` tag, never as `![alt](url)`.** SveltePress's own markdown pipeline converts every `![]()` into an `<enhanced:img>` custom element, meant to be compiled into a real `<img>`/`<picture>` at build time by `@sveltejs/enhanced-img`'s Vite plugin (`enhancedImages()`) — but that plugin isn't registered in `vite.config.ts`, so the tag passes straight through to the browser as an inert, unrecognized element: no image, no error, no console warning, nothing in Network either (confirmed live on `guide/scale-hierarchy/+page.md`, the first page on the publication to actually embed a content image). Registering `enhancedImages()` was considered and rejected: the package is explicitly experimental (pre-1.0), and its own resolver can't `import` a file that lives in `static/` (SvelteKit's public dir isn't part of Vite's module graph) without a special `/static/`-prefixed path convention its own error message documents — real, but untested, complexity to take on for a handful of images across the publication. A raw `<img src="/path/to/file.png" alt="...">` tag sidesteps all of it: same "content the auto-pipeline doesn't handle, write real HTML instead" convention already used for `[Citation.svelte](src/lib/theme/components/Citation.svelte)`'s `<span id="ref-N">` anchors, and it survives `allowDangerousHtml`'s opaque-string passthrough unmangled since `img` is a real HTML5 tag name (same reasoning as `<span>`, see the raw-HTML note above). If a future need for real build-time image optimization (responsive `srcset`, avif/webp) comes up across many images rather than one, revisit wiring in `enhancedImages()` properly then, including the `/static/`-prefix path handling — not before. **Four Foundations pages now carry one such illustration each** (added 2026.09.14, hand-placed by Kevin directly rather than through a session): Scale Hierarchy, Density Tiers, Street Types & Classifications, and Design Speed & Speed Limits, each a single PNG under `static/diagrams/` (`{page-slug}-diagram.png`) placed as the first element right after the page's `<script>` block (before `<RelatedMedia>` on the two pages that also carry one — the illustration leads, Related Media follows). `base.css` gives every standalone raw `<img>` in page prose a themed rounded-corner/hairline-border/shadow treatment automatically (`.cw-content > img` for an img that's its own top-level block, `.cw-content p > img:only-child` for one CommonMark wraps in a paragraph) — no per-image class needed, this applies to any future illustration added the same way.

**Wide tables scroll horizontally in their own box instead of overflowing the page.** `src/lib/theme/markdown/table-scroll.ts` (a rehype plugin) wraps every markdown `<table>` in `.cw-table-wrap > .cw-table-scroll > table` plus a small hidden-by-default "scroll for more" hint, at build time — no per-table authoring needed, this applies to every table on every page automatically. `base.css`'s `.cw-table-*` rules add a CSS-only scroll-shadow (the Lea Verou two-gradient trick, no JS) and a themed thin scrollbar to `.cw-table-scroll`; `src/lib/theme/layout.ts`'s `initTableScrollHints()` (called from `GlobalLayout.svelte` on mount and after navigation) measures each table and only shows the hint text when a table actually overflows. Deliberately a wrapper div, not CSS `display: block`/`overflow-x` on the `<table>` element itself (an earlier version of this fix): forcing a table's own computed `display` off `table` strips its implicit ARIA table/row/cell roles in some browsers, breaking screen-reader table semantics — the wrapper keeps the table's native display untouched. A simple 2-column table still renders at full width with no scrollbar; only a table wide enough to need it (many columns, or long unbreakable content) triggers the scroll box.

**`vite.config.ts` is the single source of truth for site content structure** — navbar links, the manual sidebar tree (keyed by route prefix, e.g. everything under `/guide/` uses the `sidebar['/guide/']` entry), GitHub link, edit-link template, site title/description. This is the file to edit for day-to-day content/nav work; `src/lib/theme/` should rarely need touching once the visual direction is set. The sidebar shown for any page is whichever key in `sidebar` the current URL starts with (same model as SveltePress's own default theme). There is no auto-generated sidebar from the routes folder — it's manual by design, since it needs to map onto the Functional Classification / density-tier hierarchy rather than a generic path tree.

**Brand tokens:** `src/lib/theme/styles/tokens.css` is the single place all colors/type/spacing live, as CSS custom properties — components reference tokens, never raw hex values. **Synced to the real Brand Guide palette**, with one documented exception still marked PLACEHOLDER in the file: `--cw-danger` (the guide doesn't define one; decoupled from `--cw-freeway` since Freeway's real color is a neutral gray, not alarming). `--cw-intersections` is no longer a placeholder: as of 2026.08.30 it's a full site-only 6-tier ramp (`--cw-intersections-undeveloped` through `--cw-intersections-core`), built from a single base color (`#8a5a13`, the exact hex the old placeholder already used, so nothing that referenced the token changed color) with the same constant-hue/constant-saturation, evenly-stepped-lightness method the guide's own four ramps use. **Flagged, not fixed:** that hue sits within about a degree of `--cw-amber`, the color the guide reserves exclusively for the unsourced-claim flag and pattern-illustration highlighting — Intersections & Crossings now reads visually close to "amber warning" everywhere its color appears (PatternCard's left edge, PatternIndexCard's hover border and image tint). A deliberate user choice (they supplied the exact hex), documented on `/about/brand-guide/`'s Functional Classification ramps section rather than silently avoided. Key distinctions, easy to get wrong:

- `--cw-teal` is the raw brand hue (`#00A896`), for self-contained solid fills (buttons, badges, chips) where contrast against the page background doesn't apply. `--cw-primary` is a darkened/lightened variant of the _same_ hue, for text or thin accents sitting directly on the page background (hover states, active nav, focus ring, note admonition) — raw teal only reaches 2.86:1 on paper, under the 4.5:1 text minimum.
- `--cw-ink-fixed` / `--cw-paper-fixed` are non-theme-varying (defined once, never overridden in `[data-theme='dark']`), for text on a fill that's itself fixed (primary/dark buttons, the unsourced-claim flag, evidence chips). Using `var(--cw-ink)` there instead would flip to near-white in dark mode and go invisible against its own fixed-dark or fixed-colored background — this bit Button.svelte's "dark" variant during the sync, worth remembering.
- `--cw-link` / `--cw-link-hover` are the Brand Guide's indigo, used only by `base.css`'s global `a` rule for content hyperlinks, distinct from `--cw-primary`/`--cw-teal`.
- `--cw-amber` is reserved exclusively for the unsourced-claim flag and pattern highlighting per the guide, **never a general UI accent** — the global `:focus-visible` ring and the navbar active-link underline were both moved off amber onto `--cw-primary` for this reason (amber also only reached 1.97:1 against light paper as a focus ring, failing the 3:1 UI-component minimum). The `:::warning` admonition still uses amber and is a known, deliberately unresolved conflict with this rule, flagged in the Brand Guide page rather than silently changed.
- `--cw-local/-collector/-arterial/-freeway` each have a full 6-tier ramp (`--cw-local-undeveloped` through `--cw-local-core`, etc.) plus a single representative token (`--cw-local`, etc.) used by PatternCard's border accent, mapped to whichever tier clears (or gets closest to) 4.5:1 contrast — this differs by classification and by theme, see the comments in `tokens.css`. `-soft` variants reuse each classification's own lightest (Undeveloped) tier in light mode; dark mode needs hand-picked dark tints instead, since a near-white pastel looks wrong as a "soft" background on a dark page.
- `PatternCard.svelte`'s Pattern ID text is always `var(--cw-ink)`, never the classification color, per the guide ("a constant identity mark distinct from classification color") — this also happens to be load-bearing: Arterial and Freeway's real ramp colors don't clear 4.5:1 as text on either paper tone.

**Adapter:** `@sveltejs/adapter-static`, `strict: true`, output to `build/` — the whole guidebook prerenders to static HTML with every pattern page a real crawlable URL. `src/routes/+layout.ts` turns on prerendering and trailing-slash URLs; `src/routes/+layout.svelte` is deliberately minimal since SveltePress wraps it in `GlobalLayout`.

**Retiring or redirecting a page (first used 2026.09.02, the Commercial Arterial → Stroad merge):** a real HTTP redirect isn't possible from inside the app on a fully static, server-less build — SvelteKit's own `redirect()` only works from a server `load` function, which `adapter-static` doesn't run at request time. The fix is `static/_redirects`, Netlify's own static-redirects file format (`/old-path/ /new-path/ 301`, one rule per line): Netlify reads it directly at the CDN edge, no server or build-time plugin involved, and it gets copied into `build/` like any other static asset. Delete the retired route folder entirely rather than leaving a stub page (a stub would itself need `strict: true`-safe content and just adds a page that immediately fights the redirect). This can't be verified in `pnpm run dev`/`pnpm run preview` — neither reads `_redirects` — only confirm the redirect rule is present in `build/_redirects` after `pnpm run build`; the actual redirect only takes effect once deployed to Netlify.

**"Last updated" date** (`PageLayout.svelte`'s footer, next to "Suggest changes to this page"): sourced from `src/routes/+layout.server.ts`, which runs `git log -1 --format=%cI -- <that route's +page.md>` once per route at build time and formats the result, `null` (no line rendered) if the file has no commit yet or git isn't available. Deliberately **not** the file's filesystem mtime — a fresh CI checkout (Netlify's included) resets every file's mtime to the checkout moment, not its real last-edit date, so mtime would just always show the build date. This is a real server `load` function (needs `@types/node` for `child_process`/`process`), but it still fully prerenders under `adapter-static`: it runs once per route during the build and the result is baked into the static output, no runtime server involved, same "computed at build time" reasoning `siteVersion()` (below) also uses.

**Navbar CalVer version (fixed 2026.09.01):** `Navbar.svelte` no longer computes its own version — it reads `page.data.siteVersion`, set by `siteVersion()` in the same root `src/routes/+layout.server.ts` described above (`src/lib/site.ts`'s `calVerToday()` is gone; `formatCalVer(year, month, day)` is its pure-formatting replacement, called from both branches below). The original design (a plain `new Date()` read wherever `calVerToday()` was called) worked in `pnpm run dev` but was wrong in production: a prerendered build's wall clock reflects whenever Netlify happened to actually run that build, not the date of the commit being built, and those two dates silently diverge any time Netlify rebuilds the same commit later without a fresh push (a manual "Trigger deploy" / "Clear cache and deploy site" click, or an automatic retry) — confirmed live on 2026.09.01, when the navbar showed a date one day ahead of every page's own git-derived "Last updated" text after exactly that kind of same-day rebuild. `siteVersion()` fixes this by keying the version to the actual last commit's date (`git log -1 --format=%cI`, no path filter, i.e. `HEAD`) instead of the wall clock, gated on SvelteKit's `dev` flag from `$app/environment`: `pnpm run dev` still shows a live current-date read (there's no meaningful "last commit" to key off mid-edit), but `pnpm run build`/`pnpm run preview`/the real Netlify build all show the last commit's own date, which only changes when new content is actually pushed, and stays identical no matter how many times that same commit gets rebuilt. If this ever needs re-diagnosing: compare the navbar version against any page's own "Last updated" text — they're computed by the same `git log` mechanism now and should never disagree the way they did before this fix.

**`llms.txt` / `robots.txt` / `sitemap.xml`:** `src/routes/{llms.txt,robots.txt,sitemap.xml}/+server.ts` are `+server.ts` endpoints, not files under `static/`. `src/lib/server/content.ts` globs every `+page.md` at build time (`import.meta.glob(..., { query: '?raw' })`, parsed with the `yaml` package) and reads each page's `llms` frontmatter field (falls back to `description`, then `title`) to build `llms.txt`; `sitemap.xml` uses the same `getSitePages()` helper to list every page's absolute URL with a build-date `<lastmod>`. **Pattern ID scheme (corrected to nine prefixes, 2026.08.31):** `[PREFIX]-[CTXCODE]-[##]` with an optional trailing `(DENSITY)` suffix (`UND`/`RRL`/`SUB`/`CPT`/`URB`/`COR`), e.g. `LOC-BBG-12`. `PREFIX` encodes Scale: `NET` (Network), `CDR` (Corridor), `FAC` (Facility), and `ELM` (Element) are flat, non-subdividing prefixes, one per Scale; `LOC`/`COL`/`ART`/`FRE` (the four Functional Classifications) and `INT` (Intersections & Crossings, cross-cutting, its own top-level code rather than nesting under one classification) are the five prefixes at the Segment/Intersection scale, the only Scale that subdivides by Functional Classification. `CTXCODE` is a hand-designed three-letter mnemonic; each classification's baseline/default entry uses `DEF` (not the classification's own letters). Two different prefixes can legitimately share the same `CTXCODE` (`ELM-TRB-23` Traffic Barrier and `INT-TRB-02` Turbo-Roundabout), not a bug, same precedent as `COR`/`COL`. **The number is two digits, assigned once per Typology within its prefix in first-added order, and is never reassigned or reordered to match display/alphabetical order later** — this is the rule that broke twice during scaffolding (see `src/routes/patterns/+page.md` for the current full mapping, and the pattern-pages project memory for the format's version history if a stale mapping ever surfaces again). **Two more precise root causes found for this same general class of bug, while building the Speed & Modal Hierarchy card (2026.09.02) — both now-understood special cases of "content inside a nested component slot isn't parsed as markdown the normal way," not two separate bugs:** (1) Indenting a markdown-embedded Svelte component's content by 4+ spaces for source readability, when that content starts right after a blank line, gets parsed as a CommonMark indented code block, silently breaking any markdown inside it (an ordered list rendered as literal `1. Pedestrian` text, and swallowed a same-line raw `<a>` tag into the code block where it rendered as escaped text instead of a link). Fix: never indent multi-line component content, even though every sibling tag around it is indented — write it flush left. (2) A markdown-embedded component tag carrying a complex prop value (an object or array literal, e.g. `rows={[{ tiers: [...] }]}`) fails CommonMark's own HTML-block-recognition regex and gets treated as plain paragraph text instead of a component, **specifically when a blank line immediately precedes it** — confirmed by the exact same tag succeeding once the blank line above it was removed (making it a continuation of the prior tag's line instead of a fresh block) and failing again when the blank line was restored. A tag with only simple string/number attributes doesn't hit this. Fix: never put a blank line directly before a component tag that has an object/array-literal prop; self-closing vs. open+close tag form didn't matter once this was fixed. Both fixes are now baked into every page using `SpeedModalHierarchyCard`/`SpeedLimitSection`/`ModalHierarchySection` — copy their markdown structure (flush-left, no blank line before a complex-prop tag) rather than the more readable indented style used elsewhere on the site, if adding a similarly nested component in the future.

## Media Gallery & Related Media (2026.09.04)

**A new content shape, distinct from Patterns/Retrofit Strategies/Guide pages, built for this feature: data records instead of full content pages.** Patterns, Retrofit Strategies, and Guide pages are each a hand-authored `+page.md` with real prose and their own route; there is no queryable collection behind them, the "index" pages are hand-typed lists of card components. Media items have no route of their own and need to be filtered/sorted/cross-referenced, so they're stored as one TypeScript file per entry under `src/lib/data/media/entries/` (e.g. `med-001.ts`, exporting a `default` object typed against `MediaItem` in `src/lib/data/media/types.ts`), globbed at build time by `src/lib/data/media/index.ts` (`getMediaItems()`, `getMediaItemsFor(pageId)`) the same `import.meta.glob` mechanism `$lib/server/content.ts` and `$lib/theme/blog.ts` already use for `+page.md` frontmatter. `.ts` over `.json`: identical build-time-only performance either way, but `.ts` gets checked by `pnpm run check` (catches a typo'd `endorsementStatus` or a missing field at edit time; JSON has no schema enforcement). **This is the pattern to reuse for any future data-record content type** (not a full page) that needs filtering or cross-referencing, the same way Patterns/Retrofits are the pattern to reuse for a future full-page content type.

**`MediaItem` schema** (`src/lib/data/media/types.ts`): `id` (permanent, e.g. `MED-001`, never reused), `type` (`video | podcast | article`), `title`, `url`, `sourceName`, `sourceIcon` (optional — full external URL to hotlink, or a local `/`-prefixed static path; omit for a generic Lucide fallback icon keyed to `type`, see `MediaCard.svelte`), `image` (optional; as of 2026.09.26 a SELF-HOSTED local path, `/media-assets/med-NNN.jpg`, never a hotlink: the 21 existing previews were downloaded once and resized to 640px wide; omit for the shared placeholder `static/media-assets/media-placeholder.svg`), `blurb` (how the item relates to CS content, not a neutral summary), `endorsementStatus` (`aligned | context-only | counterexample`, always rendered as a uniform neutral pill with no color-coding, a deliberate house rule), `patternTaxonomyTags` (reuses the Local/Collector/Arterial/Freeway vocabulary), `mediaTags` (locked vocabulary: `Case Study`, `Explainer`, `Interview`, `News/Advocacy`, `Historical` — do not add a value without confirming first), `relatedTo`, `dateAdded` (ISO 8601). 45 entries exist as of 2026.10.14 (21 as of 2026.09.14, added across four batches; `MED-022`-`MED-045` are the fifth, below): `MED-001` (Not Just Bikes, continuous sidewalks); `MED-002`–`MED-005` (City Beautiful ×3, BicycleDutch ×1); `MED-006`–`MED-020` (Global Cycling Network, Not Just Bikes, City Beautiful, Safe By Design, Streetcraft, Road Guy Rob); **`MediaFilters.svelte` mobile redesign (2026.09.04, two follow-up rounds after initial ship):** the desktop 2-column layout above is only half the story below 940px. Round 1 found a real bug: the original single always-`position: sticky` implementation stayed pinned to the top of the viewport in the mobile stacked layout too, so scrolling made it visually overlap the results grid scrolling underneath it (sticky only makes sense next to a much taller sibling column, the desktop case). Round 2 was a design request: a permanently-expanded filter panel was also eating most of the mobile screen before any results were visible, and the user wanted it collapsed by default on mobile with no toggle at all on desktop, repositioned to sit just before the results count/grid rather than above the page title.

The fix ended up as **two small mounts of the same component, not one instance repositioned with CSS**, via a `variant: 'desktop' | 'mobile'` prop: `variant="desktop"` renders a plain `<aside>`, always expanded, no toggle affordance, CSS-hidden below 940px — this is what `GlobalLayout.svelte` mounts in the toc-column slot, unchanged in spirit from the original design. `variant="mobile"` renders a real `<details>`/`<summary>` disclosure, collapsed by default (no `open` attribute, works with no JS via native browser semantics), CSS-hidden at 940px and up — this is mounted separately, inline in `/media/+page.md`'s own markdown between the intro paragraph and `<MediaGallery />`, landing it exactly where a reader expects a filter control: right before the results, not above the title. Both instances read/write the same `media-filters.ts` stores, so they're never out of sync, just two different rendering locations for the same underlying state. **The reason it's two mounts instead of one repositioned element:** the desktop slot (a `GlobalLayout`-level grid sibling) and the mobile position (a descendant inside the page's own content column, itself nested in a completely different grid container) are genuinely different DOM subtrees — no CSS mechanism (`order`, `grid-area`, positioning) moves an element between two unrelated grid contexts. If a future page needs "different content/position per breakpoint, sharing one piece of state," this two-small-mounts-plus-shared-store pattern is the one to reuse, not a single repositioned element.

## Homepage hero background: native canvas ink-halftone effect (Item 19, 2026.09.11)

**`src/lib/theme/components/InkHalftone.svelte`** replaces `.hero-lines` (the old `repeating-linear-gradient` diagonal texture) on the homepage `Hero.svelte`, and only that layer: `.hero-glow` and `.hero-bleed`'s solid ink background are untouched, same DOM position, same stacking order. It's a `<canvas>` + `requestAnimationFrame` grid of small dots (10px spacing) whose radius swells from `0` (fully invisible at rest) up to a peak, confined to a couple of curving Bezier "road" paths drawn through the hero so the reactive shape itself reads as a street rather than a generic wipe. Built natively per the source ticket's explicit "no third-party effects bundle, no purchase" requirement, inspired by (not copied from) a paid canvas effect the user linked for reference (getdesign.md's "Ink Halftone").

**What actually drives the swelling is layered value noise, not a wave.** This went through several rounds of user feedback before landing here, each round a real lesson for any future "animated background" request:

- v1 (discrete traveling pulses along the roads, Gaussian falloff) — read as "too fast" and "too predictable," literally two clean blobs repeating on an obvious cycle.
- v2 (summed sine waves along each road's arc length) — fixed the predictability but read as one blob shape breathing in and out, and was "too slow."
- v3 (2D fractal value noise — `hash()`/`valueNoise()`/`fbm()`, several octaves at different spatial scales summed together) — this is what actually produces blobs of varying size and shape, since small- and large-scale octaves reinforce or cancel differently at every point; a single-frequency wave structurally cannot do that no matter how it's remapped or how many terms are added.
- Final tuning rounds: direction moved from a per-road flow vector to a per-octave one (three octaves biased 75–110° i.e. rightward with vertical wander, one large/slow/low-weight octave drifting the other way, so "most blobs move right, a few don't" instead of a uniform direction or a 50/50 split); scale range widened (100–720px) for a bigger min/max size spread; `NOISE_FLOOR` lowered to allow more simultaneous blobs; `PEAK_RADIUS` raised for bolder dots at full swell.

**Two real bugs hit building this, both worth remembering for any future "invisible until triggered" animated grid:**

- Setting `BASE_RADIUS = 0` (so a resting dot draws nothing) also silently broke the `prefers-reduced-motion` static frame, since that frame reused the same constant — reduced-motion users would have seen nothing at all. Fixed with a separate `STATIC_RADIUS` constant used only for that one frame.
- An early version added small random per-dot position jitter for a "hand-set halftone" look; this broke the grid's own row/column alignment, which reads as a bug (a halftone dot grid is expected to actually be a grid) rather than an organic touch. Removed entirely — position jitter and "organic" character are not the same thing; the organic quality here comes entirely from the noise-driven radius, not from perturbing the grid itself.

**Iteration reality check for future visual/motion effect requests:** none of the tuning values above (spacing, scale range, floor/ceiling threshold, direction split, speed) were derivable from the ticket or from first principles; every one of them took a round of "publish, watch it run for a few seconds in the actual dev server, compare against feedback" to land right. Budget for that when scoping a similar request rather than expecting one shot to nail speed/size/density/direction simultaneously. **Confirmed true again 2026.09.14:** `PEAK_RADIUS` bumped from `3.4` to `4.4` (Kevin's own direct edit, bolder dots at full swell), one more round of the same "the ticket/first pass gets it in the right neighborhood, the exact number still needs a live look" pattern.

## GuideDiagram, the img/height:auto bug, and AuthorPhoto (2026.09.22)

**`src/lib/theme/components/GuideDiagram.svelte`** replaces the raw `<img>` tag on the four Foundations pages that embed a full-width topic diagram (Density Tiers, Design Speed & Speed Limits, Scale Hierarchy, Street Types & Classifications). `src`/`alt` are required, matching the raw tag's own required attributes; four more props are optional and independent of each other: `width`/`height` (real pixel dimensions as actual HTML attributes, not CSS — lets the browser reserve the image's layout space from its own attribute-derived aspect ratio before a lazy-loaded image finishes downloading), `aspectRatio` (a CSS `aspect-ratio` string, for when the ratio is known but not the exact pixel size — ignored if `width`/`height` are both given), and `caption` (wraps the image in a real `<figure>`/`<figcaption>` instead of a bare `<img>`, no extra ARIA needed for that semantics). ## Pattern viewer choices within a layer (2026.10.19)

Facets now drive real choices; first used on Collector Default (`col-def-01.ts`: `parking` none/left/right/both on every rung but Dutch, `bikes` street/sidewalk on the Commonway rung only). Rules:
- **A facet applies to a configuration when one of its entries names it in `when`** (`facetApplies()` in `state.ts`); elsewhere its buttons are disabled with "Doesn't apply to ...". No separate flag.
- **Generate the combinations in the data file** with small `side()`/`street()`/`describe()` helpers, never by hand; keep segment ids identical in every combination (the diff and "moved" match by id). `when` must be typed `Record<string, string>` or svelte-check rejects the union.
- Facets render as button rows (`.pvc__choices`), not dropdowns. Compare can target `facet:option` (`CompareTarget`, also `?compare=parking:both` in the URL): pane two is the same rung with that choice, and its "What changed" counts from pane one. Panes carry a `key` (two panes can share an entry id).
- `diffStreets` now reports **moved** strips (heaviest common subsequence by `STAY_WEIGHT`, so travel modes are the ones reported) with their new neighbors, nearer-property-line first so both sides share one number, and a **right-of-way** change line. Level changes are reported too.
- **`Segment.level`** (`road | intermediate | sidewalk`, default from `levelOf()` in `geometry.ts`; `isRaised` and the art's `isRaisedSegment` both derive from it). `intermediate` sits at 0.4 of the curb; where it meets a sidewalk, `edgeStripLow()` draws a sloped edge strip (section, slice) instead of a curb. `Segment.shortLabel` names a strip too narrow for its `label`.
- Descriptions end with the right of way ("Right of way: 60 ft."), since widths now change with the choices.
- **The ladder switches to `CONFIG_COMPACT_LABELS`** (Base, Complete...) when its short labels overflow, measured in `PatternViewerControls` (run the check with `untrack`, or it loops: `effect_update_depth_exceeded`). Its tooltip is clamped to the ladder's width and flips below it inside a scrolling panel (full view).
- **Puppeteer element screenshots** of the controls once painted the first button row as a blank gray box; a full-page screenshot showed it fine. Don't chase that.

## Pattern viewer art (2026.10.17, Phases 1-6 of the cross-section redesign)

The cross-section and both top-down views are drawn in an illustrated style approved from a mockup (`mockups/pattern-viewer-section-v2.html`, untracked, excluded in `.git/info/exclude`). Code: `src/lib/viewer/art/` (pure functions returning SVG strings: `core.ts` conventions and seeded random, `text.ts` Inter width table, `nature.ts`, `people.ts`, `vehicles.ts`, `items.ts`, `plain.ts`, `scene.ts` for the section's sky/ground/frontage, `slice.ts` for the aligned top-down slice), `src/lib/viewer/section-layout.ts` (dimension rows and zone band), and the palette at the top of `viewer.css` (`--pvx-*`, with dark and high-contrast values).
- **The markup must be identical at build time and in the browser.** No `Math.random`, clock or DOM in art functions; every seed comes from `seedOf(segment id, ...)`, so the same strip looks the same on every rung and every load. Label widths come from the Inter table in `text.ts` on the first render, and from the browser's own font (reading font, Simplified view) after mount. Clip-path and stamp ids are prefixed with the renderer's `$props.id()` because Compare and full view put two drawings on a page.
- **Art goes in with `{@html}` inside a transformed `<g>`** (`place(x, y, scale, art)`); this works in SVG at build time (tested). Front views have the origin at the ground, y up negative; top views run along y with +y toward the reader; the Plan tab turns them 90 degrees.
- **Simplified view** hides `.art` and the clouds and shows `.art-plain` (the old outline symbols, `plain.ts`), drawn from the same placements; the slice and Plan items (`.art--slice`) stay, being plan diagrams already. A new drawn object needs both an illustrated and a plain version.

- **Lab mobile LCP rose to 3.8 s** on Collector Default with the bigger HTML (largest paint is the h1; earlier lab runs were 2.7-3.3 s). Re-measure live after deploy.
- **Phase 7 (docs and accessibility) is done:** How to Read a Pattern ("Reading the cross-section"), the Brand Guide's Pattern viewer entry (which records that the viewer's illustrated style deliberately departs from the Illustration & photography rules for hand-drawn art: full-color people, more than three per drawing, no grayscale context; those rules still govern hand-drawn illustrations) plus four zone-band contrast rows, and the Accessibility Policy's Pattern viewer section. 572 axe scans (132 viewer pages plus 11 drawn states, four modes) were clean. ## Working conventions on this repo

- **Accessibility check on every change** (axe + a whole-page accessibility review, however small the edit) is a standing rule, described in full in its own section near the top of this file. Treat it as part of "done" for any page, component, or style change.
- **Visually verify UI changes in the browser before calling them done**, not just `npm run check` (which won't catch a badge rendering illegibly small, a color barely visible in dark mode, or a hidden character leaking into visible text, all real issues found this way in past sessions). Check both light and dark mode, and at least one narrow viewport width, since this theme has real behavior differences at 940px and 560/480px breakpoints.
- **After drafting page content from a written ticket/instruction file, re-read the rendered section specifically for sentences addressed to Claude rather than to a reader** (a real, confirmed failure mode, not hypothetical — see the Bicycle Boulevard leaked-note bug in the Ticket G-J note above). A ticket file mixes real page content with meta-commentary about that content ("this citation also appears in callout 3 above," "add this verbatim," section-placement notes); it's easy for a sentence explaining _where else_ something appears to get pulled in as if it were prose for the page. A plain read-through of the finished section, asking "would a reader be confused by this sentence," catches it; `pnpm run check`/`pnpm run build` won't, since it's valid markdown that renders and links fine.
- **Compute contrast ratios rather than eyeballing color choices.** A short Python snippet (WCAG relative luminance formula) is fast and has repeatedly caught real problems eyeballing missed, e.g. the real Brand Guide amber turning out to be only 1.97:1 as a focus ring against light paper.
- When a fix surfaces an adjacent problem (a token value fix revealing a component that also needs to change, for instance), **fix genuine bugs and contrast failures directly**, but **flag pure design/content-semantics judgment calls** rather than deciding them, see "Known gaps" above for the current list of flagged-not-fixed items.
- This is a static site (`adapter-static`, deploying to Netlify). Anything touching routing, build output, or server-side code should be checked against that constraint, e.g. a new `+server.ts` endpoint needs `export const prerender = true` and, if nothing links to it, an explicit entry in `svelte.config.js`'s `kit.prerender.entries`, or it silently won't exist in the deployed build.
- **Before pushing to `main` (a push is a publish, see Deployment above), follow the publishing checklist described on `/about/release-history/`:** draft a short build note covering what content changed, what structural/site changes shipped, and anything left in a known-incomplete state, then use that note as both the commit message and a new entry in `src/lib/data/releases.ts` (newest first; one `changes` item per change, see "Changelog format" below). The site's CalVer version (shown in the navbar) is computed from the last commit's own date via `siteVersion()` in `src/routes/+layout.server.ts` (see that file's note above), so it tracks the push date rather than whenever Netlify happens to run a build; the changelog's own `releases[0]` should match what actually shipped that day, not be left stale.
- **`vite.config.ts`'s sidebar is a manual tree, `git status`/`git add` don't know about it**: adding a new page also means adding it to the relevant `sidebar['/...']` entry and, if it should show up in the Pattern Index, to `src/routes/patterns/+page.md`'s list too, or it exists but is unreachable via navigation.
- **On visual/landing-style work (the homepage build, its later redesign pass), the user wants real editorial polish, not a plain content-column render**, and will say so plainly if a first pass reads as flat or dated ("looks like an old-school 2000s site"). Concretely, this has meant: full-bleed sections that break out of the sidebar/toc grid and the 46rem prose column (see the `isHome` full-bleed pattern and the `wide` frontmatter flag, both in the Hero/EvidenceStrip/FeatureGrid note above), deliberate background contrast between sections rather than one flat page color, subtle motion (gated behind `prefers-reduced-motion`, never the only way to convey something), and named color/background treatments matching what a UI element is actually _for_ (the differentiator strip's amber-to-teal swap: amber read as a warning, not a feature highlight) over "was it the closest existing token." When the user names reference sites (Vite's and NACTO's homepages were named once) for layout/presentation ideas, actually open them in the browser tool and look, rather than working from general recollection of what those sites are like — concrete, current specifics (their two-column hero layout, glow/depth treatment, full-bleed bands) drove real decisions here that a vague memory wouldn't have.
- **Pushing to GitHub needs `GITHUB_TOKEN` from `.env`** (gitignored, never commit it): the `origin` remote is HTTPS (`https://github.com/Commonway-System/commonwaysystem.org.git`), not SSH, so a plain `git push` has no credential source of its own in a fresh environment. Use the token for that one push rather than assuming an SSH key or a cached credential helper is present. **Push procedure used 2026.09.26 (worked):** commit with the changelog build note as the message (end it with the attribution line the session's system reminder specifies), then push without writing the token into git config or the remote URL: `TOKEN=$(grep '^GITHUB_TOKEN=' .env | cut -d= -f2-); git -c http.extraheader="Authorization: Basic $(printf 'x-access-token:%s' "$TOKEN" | base64)" push origin main`. Never echo the token or print `.env`. Netlify builds on push; `pnpm run build` (which now also generates `/text/` pages) should be green locally first, and the build must have no new errors beyond the known `pnpm run check` baseline of three (`vite.config.ts` theme type, `admonitions.ts`, `heading-anchors.ts`).
- **Moving or renaming a whole route directory isn't just a file move and a link-text find/replace.** The sitewide `guide/` → `patterns/` restructure broke a page that no sitewide link grep would have caught: `src/routes/about/release-history/+page.md`'s own `<script>` block ran `import.meta.glob('/src/routes/guide/**/+page.md')` to compute a live pattern-page count, and silently started returning 0 once the pattern pages moved out from under `guide/` (no build error, no broken link, just a wrong number rendered on a live page). When restructuring routes, grep for `import.meta.glob` calls anywhere in `src/` (not just markdown links) whose path argument touches the directory being moved, same as `src/lib/theme/blog.ts` and `src/lib/server/content.ts` do for their own sections.
- **Before redoing or "fixing" something the user says is missing or wrong, verify against the actual current file/browser state first, not memory of what was intended.** A real case: after a large batch, the user said the new patterns were "forgotten" from the Pattern Index; a grep of `src/routes/patterns/+page.md` showed all six were already there from the original batch, and a live dev-server check confirmed it. The claim was wrong, not the work — spending one grep/read confirming this before touching anything avoided a pointless duplicate edit (and duplicate edits to markdown-in-`.md` component tags are exactly the kind of thing that can silently corrupt formatting, see the nested-component gotchas below). This is the same discipline as the ticket-verification rule immediately below, just applied to a spoken claim about repo state instead of a written ticket's content claims.
- **When a new content catalog needs its own index-card and detail-card components (Retrofit Strategies mirroring Patterns is the precedent so far), mirror the sibling component's mechanics exactly (image treatment, number-badge mechanism, hover states, shared layout utility class) rather than inventing new ones, and derive the new component's coloring from whichever existing classification is its closest functional/semantic peer instead of a separate palette.** Concretely: `RetrofitIndexCard`/`RetrofitCard` reuse `PatternIndexCard`/`PatternCard`'s exact shell and the `.pattern-index-grid` layout class, and Retrofit Strategies borrow Pattern classification colors (Intersection-scale strategies get the real Intersections & Crossings ramp, since Intersection patterns already have one; Corridor/Network strategies share Patterns' own still-placeholder Freeway-gray). Apply this same reasoning to the next new catalog type this site adds, rather than proposing a new palette from scratch.
- **When the user hands over a written ticket/instruction file (a spec drafted outside a live look at the repo), verify its concrete claims against the actual code rather than transcribing them literally** — this repo has now hit two real cases: a ticket describing citations as raw `<sup class="citation"><a href="#ref-N">` HTML when every page on the site actually uses the `<Citation index={N} />` component (translated silently, since it's clearly an authoring-convention gap, not a content decision); and a ticket specifying a badge color as a literal hex it described as "reusing the existing `--cw-primary-soft` token," where that token's real value produced only 1.99:1 contrast in dark mode (fixed with a proper theme-aware token, see `--cw-descriptive-ink` in `tokens.css`, rather than shipping the literal hex). Silently translate pure authoring-syntax mismatches to the site's real conventions; verify-then-fix (not just flag) a literal value that turns out to fail contrast or another concrete correctness check; still flag actual content/design judgment calls (a ticket reversing a documented convention, like Ticket B's intersection status badges, was confirmed with the user before proceeding, not decided unilaterally either way).

## Changelog format (2026.10.18)

The Release History changelog is data, `src/lib/data/releases.ts` (typed, read its header), rendered by `Changelog.svelte`; the page itself only imports it. Each release is `{ date, changes }` and each change is `{ type, area?, summary, details? }`: `type` is `new | improved | fixed | removed | note` (note = accessibility checks, known-incomplete items, link checks and other notes that aren't a change; shown last as "Checks and notes" and not counted as changes), `area` is `content | site` (notes have none), `summary` is one plain sentence without the type word (the badge says it), `details` is the full description (omit when the summary says everything). Write one change per item rather than a paragraph covering several; list them in any order, the component groups them by type. The newest release shows open (`openCount`), older ones fold behind "Show the N changes"; each date is an `h3` with id `release-YYYY-MM-DD` (in On this page; a link to it opens that release). Rules: summaries follow the editorial rules (no em-dashes, plain words); historical entries keep their date's counts and wording; backticks render as code. The 2026.10.18 conversion drafted every summary and type from the old one-paragraph items (kept unchanged as `details`, a few split where they bundled unrelated changes) for Kevin to review. `generate-agent-files.mjs`'s `log.md` parser reads the markdown copy's `###` date and `####` group headings, and `generate-text-pages.mjs` drops `.cl-more__summary`; keep both in step if the markup changes.

- **A new or changed markdown plugin (anything in `rehypePlugins`/`remarkPlugins` in `src/lib/theme/index.ts`) is not picked up by an already-running dev server**: restart it (and hard-refresh) before concluding a change "didn't apply". The built site (`pnpm run build`, then `netlify-like.mjs`) is the reliable check; count the result in `build/<route>/index.html`.
- **A rehype plugin can't match the wrapper `<div>` of a `<div class="cw-...">` block** (it is a `raw` node, the list is its sibling); see `link-cards.ts` for the state-machine over top-level nodes. A plugin may read other pages' frontmatter straight from `src/routes` with `fs` + `yaml`.
- **zsh: an unmatched glob such as `--include=*.css` aborts the whole command ("no matches found")**; use `grep -rl pattern dir` without `--include` globs, or quote them.
- **Whole-card links** are done with the first link's `::before { position: absolute; inset: 0 }` inside a `position: relative` card, other links raised with `z-index`; the focus ring is drawn on the card with `:has(> a:first-child:focus-visible)`.
