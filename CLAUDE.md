# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
pnpm install       # NOT npm install, see below
pnpm run dev        # dev server, usually http://localhost:5173
pnpm run build      # static build to build/ (HTML/CSS/JS, no server needed at runtime)
pnpm run preview    # serve build/ locally to sanity-check the static output
pnpm run check      # svelte-kit sync && svelte-check --tsconfig ./tsconfig.json
```

**Package manager is pnpm, not npm**, despite what `README.md` says: `pnpm-lock.yaml` and `pnpm-workspace.yaml` exist, there's no `package-lock.json`. The `npm run <script>` commands above are fine, they just invoke `package.json` scripts against the existing `node_modules`. But running plain `npm install` to add or update a dependency tries to re-resolve the entire tree with npm's own resolver against a pnpm lockfile, which is both wrong and extremely slow (minutes, not seconds, in testing). Use `pnpm install` for any dependency change.

There is no test suite and no lint script configured. `pnpm run check` (svelte-check) is the only automated verification step; run it after any change to `.svelte` files or theme TypeScript. It does not catch visual regressions, always check UI changes in an actual browser (see "Working conventions" below). It also does not catch a broken internal link, since that's a prerender-time check: `pnpm run build` fails outright on any same-page `#id` link or route with no matching target, thanks to `adapter-static`'s `strict: true` (see Citation.svelte's note below) — run a real build, not just `check`, after adding pages with a lot of cross-links (a pattern index, a typology-index page, etc.).

**`pnpm add`/`pnpm install` can fail with `ERR_PNPM_IGNORED_BUILDS`** if any dependency (including a transitive one, e.g. `sharp` pulled in by SveltePress's image plugin) has a native build script pnpm's default policy won't run without approval. `pnpm approve-builds` is the normal fix but needs a TTY, unavailable in a non-interactive session; the actual fix is `pnpm-workspace.yaml`'s `allowBuilds:` map (`allowBuilds: { sharp: true }`, one entry per package name) — the non-interactive equivalent, and what's committed here. If this error resurfaces for a new dependency, add its name there rather than fighting the interactive prompt.

## Architecture

This is a [SveltePress](https://sveltepress.site/) site (SvelteKit + a SveltePress theme plugin) with a **fully custom theme** — not the SveltePress default theme reskinned, but built from scratch to keep only its layout shell (sticky navbar, collapsible sidebar, on-this-page rail, prev/next footer) and replace all branding, components, and styles with Commonway System (CS) ones.

**Theme registration flow:** `vite.config.ts` calls `commonwayTheme({...})` (defined in [src/lib/theme/index.ts](src/lib/theme/index.ts)) and passes the result into the `sveltepress()` Vite plugin. `commonwayTheme` is the SveltePress theme contract: it points to `GlobalLayout.svelte` / `PageLayout.svelte` as the layout components, registers the Shiki highlighter, and wires remark/rehype plugins (`remark-gfm`, `remark-directive` for admonitions, `rehype-slug` + a custom heading-anchor plugin, `externalLinks` for automatic external-link handling, `tableScroll` for the scrollable-table wrapper, see below). Theme options (site title, nav, sidebar, GitHub link, edit-link template, footer note, Google Analytics ID) are passed through a virtual Vite module (`virtual:commonway/options`, see `optionsPlugin` in `index.ts`) so theme components can import them without prop-drilling.

**External links open in a new tab, `nofollow`, automatically, everywhere.** `src/lib/theme/markdown/external-links.ts` wires a `rehype-external-links` plugin into the rehype pipeline above: any link in `+page.md` content (citations, prose links, image-links) pointing at a different hostname than `SITE_URL` gets `target="_blank" rel="nofollow noopener noreferrer"` plus an appended icon and `.cw-sr-only` "(opens in new tab)" text, no per-link markdown authoring needed. The same `isExternalHref`/`externalLinkAttrs` helpers (`src/lib/site.ts`) are applied by hand in the few places the theme renders a hardcoded link from data rather than markdown (`Navbar.svelte`'s nav links and GitHub icon link, `PageLayout.svelte`'s edit link, `SidebarGroup.svelte`). **One real gap, confirmed by reading SveltePress's own bundled source:** a raw inline `<a href="...">` HTML tag typed directly into a `.md` file's body bypasses the rehype pipeline entirely and never gets auto-patched (SveltePress runs `remark-rehype` with `allowDangerousHtml: true` but no `rehype-raw`, so raw HTML stays an opaque string node no rehype plugin can see). Adding `rehype-raw` to close this was deliberately **not** done: it would also reparse every existing `<PatternCard>`/`<DensityChip>`/`<Citation>` component tag through an HTML5 parser that lowercases unrecognized tag names, breaking `<PatternCard>` into `<patterncard>` across every pattern page. **Always write links in `.md` content as `[text](url)`, never as a raw `<a>` tag.**

**Wide tables scroll horizontally in their own box instead of overflowing the page.** `src/lib/theme/markdown/table-scroll.ts` (a rehype plugin) wraps every markdown `<table>` in `.cw-table-wrap > .cw-table-scroll > table` plus a small hidden-by-default "scroll for more" hint, at build time — no per-table authoring needed, this applies to every table on every page automatically. `base.css`'s `.cw-table-*` rules add a CSS-only scroll-shadow (the Lea Verou two-gradient trick, no JS) and a themed thin scrollbar to `.cw-table-scroll`; `src/lib/theme/layout.ts`'s `initTableScrollHints()` (called from `GlobalLayout.svelte` on mount and after navigation) measures each table and only shows the hint text when a table actually overflows. Deliberately a wrapper div, not CSS `display: block`/`overflow-x` on the `<table>` element itself (an earlier version of this fix): forcing a table's own computed `display` off `table` strips its implicit ARIA table/row/cell roles in some browsers, breaking screen-reader table semantics — the wrapper keeps the table's native display untouched. A simple 2-column table still renders at full width with no scrollbar; only a table wide enough to need it (many columns, or long unbreakable content) triggers the scroll box.

**`vite.config.ts` is the single source of truth for site content structure** — navbar links, the manual sidebar tree (keyed by route prefix, e.g. everything under `/guide/` uses the `sidebar['/guide/']` entry), GitHub link, edit-link template, site title/description. This is the file to edit for day-to-day content/nav work; `src/lib/theme/` should rarely need touching once the visual direction is set. The sidebar shown for any page is whichever key in `sidebar` the current URL starts with (same model as SveltePress's own default theme). There is no auto-generated sidebar from the routes folder — it's manual by design, since it needs to map onto the Functional Classification / density-tier hierarchy rather than a generic path tree.

**Top-level site structure (post sitewide-restructure): Home / Guide / Patterns / Reference / Blog / About**, matching the navbar array in `vite.config.ts` in that order. `/guide/` (`src/routes/guide/`) holds 7 pages now (guide section rebuild, 2026.08.30): the bare-root intro (`src/routes/guide/+page.md`, was `guide/introduction/`), grouped under 3 named sections in `sidebar['/guide/']` — **Foundations** (How to Read a Pattern, Density Tiers, Street Types & Classifications, and Scale Hierarchy, split out of the intro page into its own page since it's foundational vocabulary in its own right), **Find Your Pattern**, and **Make It Happen** (the latter two currently one placeholder page each, a planned diagnostic and a planned process walkthrough respectively, each carrying the standing `:::tip` "planned but not yet written" callout rather than an empty page). The intro page itself is listed as an ungrouped entry at the top of the array (`{ title: 'Start Here', to: '/guide/' }`, no `items`), same idea as `/about/`'s own ungrouped-at-the-top Overview item, and its sidebar/nav label is "Start Here" (distinct from its own frontmatter `title: Introduction`, which drives the page's actual `<h1>`) specifically to avoid colliding with `/about/commonway-system/`'s "The Commonway System" label. `/patterns/` (`src/routes/patterns/`) holds the bare-root Pattern Index page plus all 37 Street Typology pages, moved out of `guide/` into their own top-level section (`src/routes/patterns/{local-streets,collectors,arterials,freeways,intersections}/{slug}/`, same category/slug names as before, only the parent changed) — its own `sidebar['/patterns/']` entry has the 5 classification groups the old combined Guide sidebar used to carry. `PageNav.svelte`'s prev/next pagination is derived entirely from whichever `sidebar[...]` list matches the current URL prefix, not hardcoded per page or derived from file-tree order, so moving pages between sidebar sections was enough on its own to fix pagination, no separate per-page edits needed. `/references/` and `/blog/` are new, each a single top-level page with no sidebar entry of its own (an empty-but-present sidebar column is expected on those two, same as it would be on any route matching no `sidebar` key). The Blog index (`src/routes/blog/+page.md`) is not hand-maintained: it renders `<BlogIndex />` (`src/lib/theme/components/BlogIndex.svelte`), which globs `src/routes/blog/*/+page.md` itself via `src/lib/theme/blog.ts` and sorts by each post's `date` frontmatter field, newest first — a new post just needs a `date: YYYY-MM-DD` in its frontmatter to show up correctly ordered. `blog.ts` deliberately duplicates `$lib/server/content.ts`'s glob-and-parse-frontmatter approach rather than importing it, since `BlogIndex.svelte` is a page-rendered component and SvelteKit's build-time guard rejects any client-reachable code importing from `$lib/server/*`, even on a fully static site where that boundary doesn't functionally matter. `llms.txt`'s `SECTION_LABELS` map (`src/routes/llms.txt/+server.ts`) needs a new entry any time a new top-level section like this is added, or that section's pages fall back to showing their raw lowercase route segment as a heading instead of a proper label.

**`/about/`'s sidebar is 3 groups, not one flat list:** About (Overview, The Commonway System, Brand Guide), Development (Release History & Roadmap, Project Governance, Submit a Change, Report a Problem, Acknowledgments), Terms and Policies (Terms and Conditions, Privacy Policy, AI Policy) — each its own `collapsible: false` entry in the `sidebar['/about/']` array in `vite.config.ts`. Three of those pages still have a **display title that no longer matches their URL slug**, a deliberate, scoped rename: `/about/governance/` shows "Project Governance", `/about/contributing/` shows "Submit a Change", `/about/reporting/` shows "Report a Problem" — only each page's frontmatter `title` (which drives both the `<h1>` and the `<title>` tag, see `PageLayout.svelte`) and the sidebar/cross-link label text changed, the route folder names and URLs stayed exactly as they were, specifically to avoid re-triggering a sitewide link audit. The fourth, Acknowledgments, was later moved for real: `/about/credits/` → `/about/acknowledgments/`, route folder and all, so its title and URL slug match again. If either of these two things (the About page's own "In this section" list, or another page's inline prose) names one of these pages by title, use the current title — this bit already once during the original rename, since Contributing/Reporting/Governance/Credits cross-link each other by name in body text, not just via the sidebar.

**Content pages** live in `src/routes/`, one folder per URL segment, each with a `+page.md` (YAML frontmatter + GitHub-flavored markdown). SveltePress lets Svelte run inside markdown, so pages can `<script>` import theme components directly. Admonition blocks (`:::note`, `:::tip`, `:::warning`, `:::danger`, `:::unsourced`) are implemented in `src/lib/theme/markdown/admonitions.ts` via `remark-directive`; `:::unsourced` always renders in the reserved amber regardless of surrounding content, by design, so unsourced claims stay easy to spot before publication.

**Brand tokens:** `src/lib/theme/styles/tokens.css` is the single place all colors/type/spacing live, as CSS custom properties — components reference tokens, never raw hex values. **Synced to the real Brand Guide palette**, with one documented exception still marked PLACEHOLDER in the file: `--cw-danger` (the guide doesn't define one; decoupled from `--cw-freeway` since Freeway's real color is a neutral gray, not alarming). `--cw-intersections` is no longer a placeholder: as of 2026.08.30 it's a full site-only 6-tier ramp (`--cw-intersections-undeveloped` through `--cw-intersections-core`), built from a single base color (`#8a5a13`, the exact hex the old placeholder already used, so nothing that referenced the token changed color) with the same constant-hue/constant-saturation, evenly-stepped-lightness method the guide's own four ramps use. **Flagged, not fixed:** that hue sits within about a degree of `--cw-amber`, the color the guide reserves exclusively for the unsourced-claim flag and pattern-illustration highlighting — Intersections & Crossings now reads visually close to "amber warning" everywhere its color appears (PatternCard's left edge, PatternIndexCard's hover border and image tint). A deliberate user choice (they supplied the exact hex), documented on `/about/brand-guide/`'s Functional Classification ramps section rather than silently avoided. Key distinctions, easy to get wrong:

- `--cw-teal` is the raw brand hue (`#00A896`), for self-contained solid fills (buttons, badges, chips) where contrast against the page background doesn't apply. `--cw-primary` is a darkened/lightened variant of the _same_ hue, for text or thin accents sitting directly on the page background (hover states, active nav, focus ring, note admonition) — raw teal only reaches 2.86:1 on paper, under the 4.5:1 text minimum.
- `--cw-ink-fixed` / `--cw-paper-fixed` are non-theme-varying (defined once, never overridden in `[data-theme='dark']`), for text on a fill that's itself fixed (primary/dark buttons, the unsourced-claim flag, evidence chips). Using `var(--cw-ink)` there instead would flip to near-white in dark mode and go invisible against its own fixed-dark or fixed-colored background — this bit Button.svelte's "dark" variant during the sync, worth remembering.
- `--cw-link` / `--cw-link-hover` are the Brand Guide's indigo, used only by `base.css`'s global `a` rule for content hyperlinks, distinct from `--cw-primary`/`--cw-teal`.
- `--cw-amber` is reserved exclusively for the unsourced-claim flag and pattern highlighting per the guide, **never a general UI accent** — the global `:focus-visible` ring and the navbar active-link underline were both moved off amber onto `--cw-primary` for this reason (amber also only reached 1.97:1 against light paper as a focus ring, failing the 3:1 UI-component minimum). The `:::warning` admonition still uses amber and is a known, deliberately unresolved conflict with this rule, flagged in the Brand Guide page rather than silently changed.
- `--cw-local/-collector/-arterial/-freeway` each have a full 6-tier ramp (`--cw-local-undeveloped` through `--cw-local-core`, etc.) plus a single representative token (`--cw-local`, etc.) used by PatternCard's border accent, mapped to whichever tier clears (or gets closest to) 4.5:1 contrast — this differs by classification and by theme, see the comments in `tokens.css`. `-soft` variants reuse each classification's own lightest (Undeveloped) tier in light mode; dark mode needs hand-picked dark tints instead, since a near-white pastel looks wrong as a "soft" background on a dark page.
- `PatternCard.svelte`'s Pattern ID text is always `var(--cw-ink)`, never the classification color, per the guide ("a constant identity mark distinct from classification color") — this also happens to be load-bearing: Arterial and Freeway's real ramp colors don't clear 4.5:1 as text on either paper tone.
  The `[data-theme='dark']` block at the bottom is the dark-mode override for every token above (except the `-fixed` ones). `src/lib/theme/styles/base.css` builds base element and content typography from these tokens.

**CS-specific domain components** (`src/lib/theme/components/`, exported from `index.ts`):

- `PatternCard.svelte` — Pattern ID card; `classification` prop accepts `local | collector | arterial | freeway | intersections` and drives the left-border accent color (not the ID text, see above). Optional `status` prop (`recommended | situational | avoid`) renders a `StatusBadge` (see below) next to the classification label. Omit `status` entirely for Intersections & Crossings entries — the master Typology reference has no Status column for those, only for Local/Collector/Arterial/Freeway.
- `StatusBadge.svelte` — the `recommended | situational | avoid` pill itself, extracted out of `PatternCard.svelte` (2026.08.30) so `PatternIndexCard` could reuse the exact same badge instead of duplicating its CSS: quiet/neutral for `recommended` (no color emphasis, by design), amber for `situational` (reuses the `:::warning` token), rose for `avoid` (reuses `:::danger`).
- `PatternIndexCard.svelte` — the Pattern Index's card-grid entry (see the Pattern ID scheme note above for the full mechanism). `href`/`id`/`title`/`classification` are required; `status` is `situational | avoid` only (omit for Recommended, which gets no badge at all here, unlike `PatternCard`'s own quiet "Recommended" pill) and never applies to Intersections & Crossings; `image` is optional, omit to use the shared placeholder. The number badge is derived from `id`'s own trailing digits (`$derived`), not a separate prop, so it can't drift out of sync with the Pattern ID.
- `DensityChip.svelte` — Undeveloped → Core density-tier chip. Uses its own independent neutral-tan ramp, not the classification ramps, a deliberate site-only choice per its own comment; note this diverges from the guide's actual design (density tiers live _within_ each classification's own ramp there, not as a separate overlay) — a known, unresolved gap if this component gets revisited.
- `Citation.svelte` — numbered citation badge, and the unsourced-claim flag. Renders at 12px/semibold with a white text-shadow halo, not the guide's literal `--type-micro` (10px) — a deliberate legibility correction, documented on the Brand Guide page's Accessibility notes. Every badge links down to its source entry: `<Citation index={1} />` defaults its `href` to `#ref-1`, so any page's `## References` list must give each entry a matching anchor — write it as `1. <span id="ref-1"></span>Source text...`, a raw inline `<span>` is safe here (unlike a raw `<a>` tag, see the external-links note below) since it's a real HTML5 tag name that survives `allowDangerousHtml`'s opaque passthrough unmangled. `base.css` gives `[id^='ref-']` the same `scroll-margin-top` as headings so the jump clears the sticky navbar. Override `href` explicitly if a page's reference numbering doesn't follow the `ref-{index}` pattern, or (like Brand Guide's illustrative `<Citation index={14} href="#" />` demo, which has no real reference list behind it) the target genuinely doesn't exist: `adapter-static`'s `strict: true` prerendering fails the whole build on any same-page `#id` link with no matching element, so an un-overridden default `href` there breaks `pnpm run build`, not just a soft dead link. `href="#"` (no fragment id) sidesteps that check since there's nothing to validate.
- `EvidenceChip.svelte` — Legal / Evidence-based / Precedent-based tier chip (`tier` prop: `legal | evidence | precedent`). Standing house rule as of the sitewide evidence-tier rollout: every citation added to any page's `## References` list, from now on, must carry an `<EvidenceChip tier="..." />` right in that list item at the same time the citation is added — Legal/regulatory (a statute, adopted code, or government manual), Evidence-based (a peer-reviewed study, published crash data, a formal research report), Precedent-based (a real place doing it successfully, no formal study behind it). First adopted on Density Tiers and Street Types & Classifications' `## References` lists; not yet on Bicycle Boulevard, whose 3 citations are placeholder text on demo content and are explicitly left untiered until that page gets real citations (tiering placeholders would just need redoing). Industry/association design guides that aren't government bodies (NACTO, CROW) don't cleanly fit any of the three tier definitions as written — treated as Legal/regulatory on the pages above as a judgment call, not a strict reading of the definition; revisit if this comes up again. **Placement and sizing convention:** the chip goes first, immediately after the `<span id="ref-N">` anchor and before the citation text (`N. <span id="ref-N"></span><EvidenceChip tier="..." /> Source text...`), not appended at the end — an end-of-line placement was tried first and reverted after review, since a reader has to reach the end of a long citation before learning its tier. The component's own CSS also renders it deliberately small (11px, tight padding) rather than the Brand Guide showcase's larger default, so it reads as a quiet tag rather than competing with the citation text for attention.
- `ColorSwatch.svelte`, `LogoPreview.svelte`, `ExampleCard.svelte`, `Button.svelte`, `FormControlsPreview.svelte` — Brand Guide page previews (`/about/brand-guide/`). All now token-driven, no hardcoded hex.
- `Hero.svelte`, `EvidenceStrip.svelte`, `FeatureGrid.svelte` — the homepage build (`src/routes/+page.md`). `Hero` renders its own `<h1>` rather than relying on `PageLayout`'s usual `fm.title`-driven one, so the title can sit inside the hero's own layout next to the tagline/description/actions; the homepage's frontmatter sets `hideTitle: true` to suppress `PageLayout`'s default `<h1>`, a flag `PageLayout.svelte` checks (`{#if fm.title && !fm.hideTitle}`) and only this page currently uses. The homepage frontmatter also sets `wide: true`, a second `PageLayout.svelte` opt-in flag (`class:cw-content--wide={fm.wide}`) that widens `.cw-content` from the standard 46rem prose column to 88rem, matching `Navbar.svelte`'s own `.navbar__inner` max-width, so `EvidenceStrip` and `FeatureGrid` (both inside `.cw-content`, unlike `Hero`'s own full-bleed section below) get a wider column than an article page without a third breakout mechanism. `EvidenceStrip` uses a teal/`--cw-primary-soft` card treatment (border-left accent, drop shadow), not amber: an earlier version used `--cw-amber-soft` (the `:::warning` admonition's own background), which read as a caution notice instead of a feature highlight and was also a genuine stretch of the Brand Guide's "amber reserved for pattern highlighting and the unsourced-claim flag" rule. Its "Learn how evidence tiers work" link is a plain content link with no color override, inheriting `base.css`'s global `a` styling like any other in-page link, after an earlier amber-matched version didn't read as a normal hyperlink. **A real specificity gotcha hit while building these:** `base.css`'s generic `.cw-content h1/h2/p/ul/li` prose rules (sized for markdown body text) beat a same-page single-class selector on specificity, so any of these three components' rules that override a bare element's margin/size/grid-columns needs a `:global(.some-ancestor-class)` prefix to win — and critically, once a *base* rule gets that prefix, every `@media` breakpoint rule touching the same property needs the identical prefix too, or the base rule's higher specificity wins outright regardless of which media query is active (this silently broke `FeatureGrid`'s mobile 1-column and 2-column breakpoints, and `Hero`'s mobile title font-size, during the initial build — both now fixed by prefixing the media-query rules to match).

  **`Hero`'s section is full-bleed and permanently dark**, deliberately not following the site's own light/dark toggle: `GlobalLayout.svelte` computes `isHome = page.url.pathname === '/'` and, only on that route, collapses `.shell`'s 3-column grid (`sidebar content toc`) down to a single `content` column via a `.shell--full` class (declared last in that file's `<style>` block specifically so it wins the specificity tie against the two responsive `.shell` breakpoint rules above it, at every viewport width, not just where it's declared) and hides `Sidebar`'s rendered `<aside>` at `>=940px` via `.shell--full :global(.sidebar) { display: none }`. `Sidebar` itself stays mounted unconditionally even on the homepage: below 940px it's still the only way to reach the navbar's primary links from the mobile hamburger drawer (see the `sidebar__primary-nav` note above), and `position: fixed` there already takes it out of grid flow, so it doesn't need hiding at that width. `Hero.svelte`'s own `.hero-bleed` then escapes `PageLayout`'s `.cw-content` 46rem max-width (and the padded `.page` around it) with the standard `left:50%; margin-left:-50vw; width:100vw` breakout trick, which works through however many centered ancestors sit in between since `100vw` is always the true viewport width; this only avoids introducing a horizontal scrollbar because `base.css` already sets `scrollbar-gutter: stable` on `html`. Because dark-mode's own page background (`--cw-paper` = `#141414`) is identical to `--cw-ink-fixed`, `Hero`'s `--hero-bg` custom property gets a `[data-theme='dark']` override to a deep teal-charcoal (`#0e211d`) so the hero still reads as a visually distinct band in dark mode too, not just light mode where the plain fixed-ink background already contrasts against the light paper. Its diagonal-dash background (a deliberate nod to lane markings, this being a roads-and-streets guide) and the radial teal glow behind the logomark both animate only under `@media (prefers-reduced-motion: no-preference)`, left static otherwise. Any future full-bleed section on another page should reuse this same `isHome`-gated pattern rather than inventing a second one; it currently only exists for the homepage.

Layout/UI components in the same directory (`GlobalLayout`, `PageLayout`, `Navbar`, `Sidebar`/`SidebarGroup`, `Toc`, `PageNav`, `Icon`, `ThemeToggle`, `Backdrop`, `ShareButtons`) implement the shell; `src/lib/theme/layout.ts` holds the Svelte stores for sidebar open/closed and dark mode state.

**`Navbar.svelte` below 940px (mobile-fixed 2026.08.30):** the primary nav links move into `Sidebar`'s hamburger drawer at this breakpoint, which used to leave only 2 flex groups (`navbar__start`: logo+hamburger, `navbar__end`: version+GitHub+toggle) sitting adjacent with a fixed gap, clumped on the left with empty space on the right, since nothing filled the middle once `navbar__links` (`flex: 1 1 auto`) disappeared. Fixed by unwrapping both groups into flat children of `navbar__inner` via `display: contents` inside the same `@media (max-width: 940px)` block, letting `justify-content: space-between` (added unconditionally to `.navbar__inner`, harmless at desktop widths since `navbar__links`' own flex-grow already consumes all remaining space there) spread all 5 elements evenly. Two things that looked like they'd be enough but weren't, confirmed by real measurement, not eyeballing: shrinking the version text alone still overflowed at 375px, since the full wordmark logo (147px, over a third of the viewport) was the bigger space hog, not the text; and `navbar__inner`'s existing `gap: 1.5rem` (sized for the old 2-group layout) applied 4× over across the 5 unwrapped children, ~96px of unwanted spacing, so the mobile breakpoint also sets a smaller `gap: 0.5rem` and pins `flex-shrink: 0` on all 5 items (menu button, brand, version, icon-link, toggle) — without it the icons were silently compressing below their own 36px width under crowding pressure, a real tap-target regression the fix's own test criteria were meant to catch.

**Known bug, not yet fixed (found 2026.08.30):** the mobile hamburger button doesn't actually toggle the sidebar drawer open on any viewport — `sidebarOpen`'s store state does flip (confirmed via the button's own `aria-label` changing between "Open/Close navigation"), and `Sidebar.svelte`'s `.sidebar--open { transform: translateX(0) }` CSS rule is present and higher in source order than the base `.sidebar` rule, but the drawer's computed `transform` never actually changes, so it stays off-screen. Confirmed on an untouched copy of `main` in an isolated `git worktree`, so this predates any recent session's changes and isn't caused by the mobile navbar layout fix above. Net effect: on any viewport narrower than 940px, the primary nav links and the current page's sidebar tree are currently unreachable through the hamburger button. Root cause not yet diagnosed.

- `ShareButtons.svelte` — the "Share:" row in `PageLayout.svelte`'s footer (X, Facebook, LinkedIn, Reddit, Bluesky, email, copy-link), shown on every page uniformly. Every network is a plain `<a>` to a public share-intent URL (`x.com/intent/tweet`, not `twitter.com`, confirmed live — `twitter.com` still works but just redirects), **no share SDK/widget script** (Twitter's `widgets.js`, Facebook's SDK, AddThis, ShareThis) — those set their own third-party cookies, which would contradict `/about/privacy-policy/`'s "no other tracking beyond what's listed" claim. Copy-link is the one bit of real client JS (Clipboard API), fails silently if unavailable. Its root element is a `<span>`, not a `<div>`: it mounts inside `PageLayout.svelte`'s `<p class="page__meta">`, and a block-level root there is invalid HTML that browsers silently "fix" by force-closing the `<p>` early — easy mistake to reintroduce if this component gets restructured. The visible "Share:" label sits in that same paragraph's own inline text flow rather than inside the icon row's `inline-flex` container, since centering it against the icons' taller box height (not the surrounding text's baseline) is what caused a real 1-2px vertical misalignment, only visible at the one width wide enough to fit "Suggest changes…", "Last updated…", and the share row on one line.
- `Icon.svelte`'s `filled` prop (default `false`, preserves every original icon's stroke-only rendering): the share-button brand marks (`facebook`, `linkedin`, `reddit`, `bluesky`) render `fill="currentColor" stroke="none"` instead, since a solid logomark only reads correctly filled, not traced as a line icon (that's also why `github`, the one pre-existing "logo" icon, looks slightly off as a stroke — established behavior, not touched). The shared `<path>` also always carries `fill-rule="evenodd"`, needed only so the `reddit` mark's eye circles punch through as holes rather than double-filling invisibly on top of the head circle (a no-op for every stroked icon and every filled icon without overlapping subpaths). `reddit` and `bluesky` are simplified original glyphs, not pixel-exact traces of the real logos — verify any new icon by rendering it standalone (not just trusting the SVG path data by eye) before shipping.

**Adapter:** `@sveltejs/adapter-static`, `strict: true`, output to `build/` — the whole guidebook prerenders to static HTML with every pattern page a real crawlable URL. `src/routes/+layout.ts` turns on prerendering and trailing-slash URLs; `src/routes/+layout.svelte` is deliberately minimal since SveltePress wraps it in `GlobalLayout`.

**"Last updated" date** (`PageLayout.svelte`'s footer, next to "Suggest changes to this page"): sourced from `src/routes/+layout.server.ts`, which runs `git log -1 --format=%cI -- <that route's +page.md>` once per route at build time and formats the result, `null` (no line rendered) if the file has no commit yet or git isn't available. Deliberately **not** the file's filesystem mtime — a fresh CI checkout (Netlify's included) resets every file's mtime to the checkout moment, not its real last-edit date, so mtime would just always show the build date. This is a real server `load` function (needs `@types/node` for `child_process`/`process`), but it still fully prerenders under `adapter-static`: it runs once per route during the build and the result is baked into the static output, no runtime server involved, same "computed at build time" reasoning as `calVerToday()`.

**`llms.txt` / `robots.txt` / `sitemap.xml`:** `src/routes/{llms.txt,robots.txt,sitemap.xml}/+server.ts` are `+server.ts` endpoints, not files under `static/`. `src/lib/server/content.ts` globs every `+page.md` at build time (`import.meta.glob(..., { query: '?raw' })`, parsed with the `yaml` package) and reads each page's `llms` frontmatter field (falls back to `description`, then `title`) to build `llms.txt`; `sitemap.xml` uses the same `getSitePages()` helper to list every page's absolute URL with a build-date `<lastmod>`. New pages appear in both automatically. Because prerendering is on, all three compile down to plain static files in `build/` at build time, same as every page, no server needed at runtime, safe for a Netlify/adapter-static deploy. Nothing links to any of them, so they're listed explicitly in `svelte.config.js`'s `kit.prerender.entries` or the crawler skips them. `robots.txt` points at `sitemap.xml` via a `Sitemap:` line. `src/lib/site.ts` holds the canonical `SITE_URL` used for all three routes' absolute links, plus the `isExternalHref`/`externalLinkAttrs` helpers (see external-links note above).

**Google Analytics:** `src/lib/theme/components/GoogleAnalytics.svelte`, rendered once from `GlobalLayout.svelte`, injects the gtag snippet via `<svelte:head>` when `options.googleAnalyticsId` is set (currently `G-VCDS38HY87` in `vite.config.ts`) **and** `import.meta.env.PROD` is true, so `pnpm run dev` never sends traffic. SveltePress's own default theme has a built-in `ga` config option that auto-injects this, but that's a default-theme-only feature; `@sveltepress/theme-default` isn't installed here (this theme is fully custom, see top of file), so it had to be hand-built. **Do not write a literal `<script>...</script>` tag inside this component's own `<script>` block** (even inside a string or comment) — Svelte's compiler misparses the literal substring `<script` as a nested tag boundary regardless of quoting; the tag text is built from concatenated string pieces (`` `<${'script'}` ``) instead, so the literal substring never appears in the source.

**JSON-LD structured data (added 2026.08.30):** every page emits `<script type="application/ld+json">` blocks via `JsonLd.svelte`, built from pure functions in `src/lib/theme/schema/` rather than hand-authored per page, keyed to `schema-dts` types for compile-time-checked shape. Two injection points, split by what each layout actually has access to: `GlobalLayout.svelte` renders the sitewide singletons (one `Organization`, one `WebSite`, `organization.ts`, computed once, page-independent) since it wraps every route; `PageLayout.svelte` renders the per-page schema (`BreadcrumbList` from `breadcrumbs.ts`, plus a template-appropriate type from `page.ts`: `TechArticle` for Guide/Reference/pattern pages, `CollectionPage`/`ItemList` for the Pattern Index sourced from the same `sidebar` data that renders its own nav, `AboutPage`/`WebPage` for About, `Blog`/`BlogPosting` for the blog reusing the existing `getBlogPosts()` helper) since only it receives `fm`. `breadcrumbs.ts` deliberately skips sidebar group headers with no `to` of their own (e.g. "Local Streets," "Foundations") rather than linking to a nonexistent classification-landing-page URL — see the Known gaps entry on those pages below. Every page's frontmatter grew a `date` field (`datePublished`, backfilled from git history the same date the "Last updated" text already showed, since no earlier true publish date is tracked) and every pattern page grew a `patternId` field (e.g. `LOC-ALY-02`), which `PatternCard`'s `id` prop now reads via `{fm.patternId}` instead of a hardcoded literal in the component tag, one source of truth for both the visible card and the `identifier` field in that page's `TechArticle` schema. `+layout.server.ts` also now returns `lastModifiedISO` (a plain `YYYY-MM-DD`, not the full `%cI` offset string) alongside the existing human-formatted `lastModified`, same git call, feeding `dateModified` in the schema.

**Pattern ID scheme:** `[CLASS]-[CTXCODE]-[##]` with an optional trailing `(DENSITY)` suffix (`UND`/`RRL`/`SUB`/`CPT`/`URB`/`COR`), e.g. `LOC-BBG-12`. `CLASS` is `LOC`/`COL`/`ART`/`FRE` (the four Functional Classifications) or `INT` (Intersections & Crossings, cross-cutting, its own top-level code rather than nesting under one classification). `CTXCODE` is a hand-designed three-letter mnemonic; each classification's baseline/default entry uses `DEF` (not the classification's own letters). **The number is two digits, assigned once per Typology in first-added order, and is never reassigned or reordered to match display/alphabetical order later** — this is the rule that broke twice during scaffolding (see `src/routes/patterns/+page.md` for the current full mapping, and the pattern-pages project memory for the format's version history if a stale mapping ever surfaces again). The `(DENSITY)` suffix is added only once a second page exists for the same Typology at a different density tier; omit it otherwise, don't pre-add it. All 37 confirmed Street Typologies from the master reference have a `+page.md` under `src/routes/patterns/{local-streets,collectors,arterials,freeways,intersections}/`, one kebab-case slug folder per Typology; three "under review" Typologies with no confirmed Functional Classification (Downtown Thoroughfare, the Avenue/Commercial Arterial cluster, Parkway) deliberately have no page, only a listing at the bottom of the Pattern Index. Each pattern page's numeric suffix is now also duplicated into a `patternId` frontmatter field (see JSON-LD note above), so the two must be kept in sync by hand if the ID scheme ever changes.

**Pattern Index page (`/patterns/`) is a card grid, not a bulleted list (rebuilt 2026.08.30):** each classification section is a `<div class="pattern-index-grid">` of `<PatternIndexCard>` tags (one per Street Typology, hand-authored in the markdown same as the old bullets were, not generated from a data file), `.pattern-index-grid`'s CSS living in `base.css` alongside `.swatch-grid`/`.demo-row` (same "Brand Guide-style layout utility" convention, not a component-scoped style) with the same 3/2/1-column breakpoints as `FeatureGrid.svelte`. The "Under review, no confirmed Functional Classification" list at the bottom stays plain bullets on purpose, those three Typologies have no pattern page or Pattern ID to build a card from. `PatternIndexCard.svelte`'s image area uses one shared placeholder graphic (`static/patterns/pattern-placeholder.svg`) by default, recolored per classification with a `mix-blend-mode: color` overlay (Suburban tier at rest, Core tier as the hover border) plus a flat `filter: brightness(90%)` on the image itself first, since the real illustrations being added are mostly-white line art and white has nowhere to go under a color blend otherwise. A pattern gets a real illustration by adding a PNG to `static/patterns/` (naming convention: `{pattern-id-lowercased}-{slug}.png`, e.g. `loc-aly-02-alley.png`) and passing it as that card's `image` prop in `patterns/+page.md`; omitting `image` falls back to the placeholder, no other change needed. As of 2026.08.30, 11 of 37 patterns have real illustrations (all of Local Streets except Bicycle Boulevard, plus Roundabout), the rest still show the placeholder pending more art. `StatusBadge.svelte` was extracted out of `PatternCard.svelte` during this build so both it and `PatternIndexCard` share one status-pill implementation instead of duplicating the CSS.

## Content model notes

- **`PageLayout.svelte` renders an `<h1>` from the page's frontmatter `title` automatically** (see `{#if fm.title}<h1>{fm.title}</h1>{/if}` in `PageLayout.svelte`). Do not start a `+page.md` body with a `# Heading` that repeats the title, it duplicates the h1. Existing pages (`guide/` bare root, `guide/how-to-read-a-pattern`, etc.) go straight from frontmatter into body text or an `##` subheading; follow that pattern for new pages.
- A companion brand guide (`../commonway-brand-guide.html`, outside this repo) defines the real, locked CS visual system: base colors (ink `#141414`, paper `#FDFAF3`, teal `#00A896`, indigo `#3D3AAB`, reserved amber `#FF9F1C`), a colorblind-checked 6-step Functional Classification × density ramp, and the Fraunces/Inter type scale. `tokens.css` is synced to it (see above); the guide itself doesn't cover dark mode, so every dark-mode value in `tokens.css` is a site-only extension, reasoned out and documented inline rather than specified by the guide.
- CS editorial rules that apply to any `+page.md` content written in this repo: no em-dashes anywhere, plain-language term introduced before its formal/technical name, and citations follow a specific numbered/dated agency-reference format (see the brand guide for the full citation and evidence-tier system referenced by `Citation.svelte` and the admonition tiers).
- The mobile hamburger drawer (`Sidebar.svelte`, `<940px`) shows the navbar's own primary links (Home/Guide/Patterns/Reference/Blog/About) above the current page's sidebar tree, not just the tree. Both live in one `<aside>` now; the primary-nav block is CSS-hidden `≥940px` since the navbar shows those links directly there. Before this fix the drawer only rendered when the current route had a page-specific sidebar, so the navbar's own links were completely unreachable on any narrow viewport, including the homepage.

## Known gaps (deliberately unresolved, not bugs to silently fix)

These surfaced across several sessions and are documented here plus inline (in `tokens.css` and on `/about/brand-guide/`) so they don't need rediscovering. Each is a real design/content-semantics call, not a clear-cut fix, raise it with the user rather than deciding unilaterally:

- The `:::warning` admonition (`src/lib/theme/markdown/admonitions.ts`) uses `--cw-amber`, which conflicts with the Brand Guide's explicit "amber is reserved exclusively for the unsourced-claim flag and pattern highlighting, never a general UI accent" rule. Not changed since there's no guide-specified alternative warning color.
- `DensityChip.svelte` renders density tiers on its own independent neutral-tan ramp. The real Brand Guide design encodes density _within_ each Functional Classification's own 6-step color ramp instead (see `tokens.css`'s `--cw-local-undeveloped` through `--cw-local-core`, etc.), which would mean `DensityChip` taking a `classification` prop too. Not implemented, current behavior is a deliberate site-only choice per the component's own comment.
- `--cw-danger` / `--cw-danger-soft` in `tokens.css` are marked PLACEHOLDER: the guide has no danger-admonition color at all, so this stays an independent site-only red. (`--cw-intersections` was the other placeholder here; resolved 2026.08.30 with a full site-only ramp, see the Brand tokens note above, itself flagging a real hue-proximity-to-amber tension rather than resolving it.)
- `guide/find-your-pattern` and `guide/make-it-happen` are deliberate placeholder pages, not stubs awaiting a wholesale rewrite: each already carries real explanatory copy about what it will become, plus the standing `:::tip` "planned but not yet written" callout, the same shape used for the site's other genuine placeholders. Each holds exactly one sidebar entry under its own named group on purpose (`Find Your Pattern`, `Make It Happen` in `vite.config.ts`'s `sidebar['/guide/']`): both are expected to split into a short sequence of pages later (a diagnostic sequence; separate who-decides/funding/how-to-request pages), and the group already exists so nothing has to move in the sidebar tree when that happens, only new items get added to each group's `items` array.
- Every real Street Typology pattern page still carries an `:::unsourced` flag pending real citations, and there are no Local/Collector/Arterial/Freeway classification-level landing pages yet within `/patterns/` — a site-structure decision the user has explicitly deferred, not forgotten.
- `/about/brand-guide/`'s "Urban main street" PatternCard demo uses `ART-UMS-07` as its illustrative ID, chosen as the next unused Arterial number (01–06 are the six real Arterial Typologies) since it isn't a real tracked Typology and the user's Pattern ID migration didn't cover it. **If a real 7th Arterial Typology is ever added, it will collide with this demo ID** — one of the two needs to move when that happens.

## Working conventions on this repo

- **Visually verify UI changes in the browser before calling them done**, not just `npm run check` (which won't catch a badge rendering illegibly small, a color barely visible in dark mode, or a hidden character leaking into visible text, all real issues found this way in past sessions). Check both light and dark mode, and at least one narrow viewport width, since this theme has real behavior differences at 940px and 560/480px breakpoints.
- **Compute contrast ratios rather than eyeballing color choices.** A short Python snippet (WCAG relative luminance formula) is fast and has repeatedly caught real problems eyeballing missed, e.g. the real Brand Guide amber turning out to be only 1.97:1 as a focus ring against light paper.
- When a fix surfaces an adjacent problem (a token value fix revealing a component that also needs to change, for instance), **fix genuine bugs and contrast failures directly**, but **flag pure design/content-semantics judgment calls** rather than deciding them, see "Known gaps" above for the current list of flagged-not-fixed items.
- This is a static site (`adapter-static`, deploying to Netlify). Anything touching routing, build output, or server-side code should be checked against that constraint, e.g. a new `+server.ts` endpoint needs `export const prerender = true` and, if nothing links to it, an explicit entry in `svelte.config.js`'s `kit.prerender.entries`, or it silently won't exist in the deployed build.
- **Before pushing to `main` (a push is a publish, see Deployment above), follow the publishing checklist described on `/about/release-history/`:** draft a short build note covering what content changed, what structural/site changes shipped, and anything left in a known-incomplete state, then use that note as both the commit message and a new entry in that page's `releases` array (newest first; a quiet day can stay a one-line `summary`, a heavier day can use a bulleted `items` list instead, per-entry, not a shape every entry is forced into). The site's CalVer version (shown in the navbar) is computed from the real clock at build time via `calVerToday()` in `src/lib/site.ts`, so it auto-tracks the push date; the changelog's own `releases[0]` should match what actually shipped that day, not be left stale.
- **`vite.config.ts`'s sidebar is a manual tree, `git status`/`git add` don't know about it**: adding a new page also means adding it to the relevant `sidebar['/...']` entry and, if it should show up in the Pattern Index, to `src/routes/patterns/+page.md`'s list too, or it exists but is unreachable via navigation.
- **On visual/landing-style work (the homepage build, its later redesign pass), the user wants real editorial polish, not a plain content-column render**, and will say so plainly if a first pass reads as flat or dated ("looks like an old-school 2000s site"). Concretely, this has meant: full-bleed sections that break out of the sidebar/toc grid and the 46rem prose column (see the `isHome` full-bleed pattern and the `wide` frontmatter flag, both in the Hero/EvidenceStrip/FeatureGrid note above), deliberate background contrast between sections rather than one flat page color, subtle motion (gated behind `prefers-reduced-motion`, never the only way to convey something), and named color/background treatments matching what a UI element is actually *for* (the differentiator strip's amber-to-teal swap: amber read as a warning, not a feature highlight) over "was it the closest existing token." When the user names reference sites (Vite's and NACTO's homepages were named once) for layout/presentation ideas, actually open them in the browser tool and look, rather than working from general recollection of what those sites are like — concrete, current specifics (their two-column hero layout, glow/depth treatment, full-bleed bands) drove real decisions here that a vague memory wouldn't have.
- **Pushing to GitHub needs `GITHUB_TOKEN` from `.env`** (gitignored, never commit it): the `origin` remote is HTTPS (`https://github.com/Commonway-System/commonwaysystem.org.git`), not SSH, so a plain `git push` has no credential source of its own in a fresh environment. Use the token for that one push rather than assuming an SSH key or a cached credential helper is present.
- **Moving or renaming a whole route directory isn't just a file move and a link-text find/replace.** The sitewide `guide/` → `patterns/` restructure broke a page that no sitewide link grep would have caught: `src/routes/about/release-history/+page.md`'s own `<script>` block ran `import.meta.glob('/src/routes/guide/**/+page.md')` to compute a live pattern-page count, and silently started returning 0 once the pattern pages moved out from under `guide/` (no build error, no broken link, just a wrong number rendered on a live page). When restructuring routes, grep for `import.meta.glob` calls anywhere in `src/` (not just markdown links) whose path argument touches the directory being moved, same as `src/lib/theme/blog.ts` and `src/lib/server/content.ts` do for their own sections.
